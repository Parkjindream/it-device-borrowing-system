# 1. บทนำ (Introduction)

## 1.1 วัตถุประสงค์ (Purpose)

เอกสารข้อกำหนดความต้องการซอฟต์แวร์ฉบับนี้จัดทำขึ้นเพื่อกำหนดขอบเขต บทบาทผู้ใช้งาน
ความสามารถ และข้อกำหนดด้านคุณภาพของระบบยืม--คืนอุปกรณ์ไอทีสำหรับสถานศึกษา
เอกสารนี้ใช้เป็นข้อมูลอ้างอิงสำหรับการวิเคราะห์ ออกแบบ พัฒนา ทดสอบ และตรวจรับระบบ
รวมทั้งช่วยให้สมาชิกทีมและผู้เกี่ยวข้องเข้าใจความต้องการของระบบตรงกัน

## 1.2 ขอบเขตของระบบ (Scope)

ระบบยืม--คืนอุปกรณ์ไอทีเป็นเว็บแอปพลิเคชันสำหรับช่วยให้นักศึกษาตรวจสอบรายการและจำนวนอุปกรณ์ที่พร้อมให้ยืม
จองอุปกรณ์ล่วงหน้า และติดตามประวัติการยืม ขณะที่เจ้าหน้าที่สามารถจัดการคลังอุปกรณ์
ตรวจสอบการจอง ยืนยันการส่งมอบและรับคืน ตรวจสภาพอุปกรณ์ และติดตามรายการเกินกำหนดได้

ระบบมีเป้าหมายเพื่อลดการทำงานด้วยเอกสารหรือการสอบถามด้วยตนเอง
ลดความผิดพลาดในการนับจำนวนอุปกรณ์ และทำให้ขั้นตอนการยืม--คืนสามารถตรวจสอบย้อนหลังได้

ขอบเขตตามข้อกำหนดเบื้องต้นประกอบด้วย: -
เข้าสู่ระบบและออกจากระบบด้วยอีเมลและรหัสผ่าน - แยกสิทธิ์ผู้ใช้เป็นนักศึกษาและเจ้าหน้าที่ -
แสดง ค้นหา และกรองรายการอุปกรณ์ พร้อมจำนวนคงเหลือ - จองและยกเลิกการจองอุปกรณ์ -
สร้างรหัสการจองและ QR Code สำหรับอ้างอิงรายการ -
กำหนดเวลาหมดอายุการจองและยกเลิกอัตโนมัติเมื่อไม่มารับภายในเวลาที่กำหนด -
ให้เจ้าหน้าที่ค้นหาหรือสแกน QR Code และยืนยันการส่งมอบด้วยตนเอง -
ให้เจ้าหน้าที่บันทึกการรับคืนและสภาพอุปกรณ์ -
ตรวจสอบรายการเกินกำหนดและใช้กฎพักสิทธิ์การจองตามที่กำหนด -
ส่งอีเมลแจ้งเตือนเหตุการณ์สำคัญ - แสดงประวัติการยืมและแดชบอร์ดภาพรวมสำหรับเจ้าหน้าที่

ฟังก์ชันที่ยังไม่ได้พัฒนา หรือยังไม่ยืนยันจากโค้ด ต้องระบุเป็นข้อกำหนดที่รอตรวจสอบ
ไม่ควรกล่าวว่าใช้งานได้แล้ว

## 1.3 ปัญหาและเหตุผลในการพัฒนา

หากไม่มีระบบดิจิทัล ผู้ใช้ต้องสอบถามหรือเดินทางไปยังจุดให้บริการเพื่อดูว่าอุปกรณ์ว่างหรือไม่
และเจ้าหน้าที่อาจต้องบันทึกข้อมูลหลายแห่ง ซึ่งเพิ่มโอกาสเกิดข้อมูลไม่ตรงกัน
ระบบนี้จึงมุ่งให้ผู้ใช้ตรวจสอบความพร้อมและจองผ่านเว็บ
พร้อมให้เจ้าหน้าที่ควบคุมการส่งมอบและรับคืนอย่างชัดเจน

`backend/` และ `db/` ก่อนระบุเป็นข้อกำหนดทางเทคนิคฉบับสุดท้าย

-   ผู้ใช้เข้าถึงระบบผ่านเว็บเบราว์เซอร์บนอุปกรณ์ที่รองรับ
-   ระบบต้องเชื่อมต่อกับบริการ Backend และฐานข้อมูลที่โครงการกำหนด
-   การส่งอีเมลต้องอาศัยบริการอีเมลและการตั้งค่าที่ถูกต้อง
-   การสร้างหรือสแกน QR Code ต้องทำงานร่วมกับหน้าจอหรืออุปกรณ์ที่รองรับ
-   เทคโนโลยีและเวอร์ชันที่แน่นอนให้ยึดตามไฟล์ dependency และการตั้งค่าของ
    Repository

## 2.4 ข้อจำกัดของระบบ (Constraints)

1.  การจองต้องไม่ทำให้จำนวนอุปกรณ์ที่พร้อมใช้งานติดลบ
2.  การสแกน QR Code เป็นเพียงการค้นหารายการ ไม่ถือเป็นการยืนยันส่งมอบหรือรับคืน
3.  การยืนยันส่งมอบและรับคืนต้องกระทำโดยเจ้าหน้าที่ที่มีสิทธิ์
4.  การพักสิทธิ์มีผลต่อการจองใหม่ตามกฎที่กำหนด ไม่ควรปิดกั้นการดูประวัติหรือการเข้าสู่ระบบ
    เว้นแต่มีข้อกำหนดอื่น
5.  การแจ้งเตือนตามกำหนดเวลาอาจใช้ Scheduled Job ตามรอบที่กำหนด
    ไม่จำเป็นต้องเป็นแบบเรียลไทม์
6.  ข้อกำหนดด้านระยะเวลาการยืม เวลาหมดอายุการจอง
    และระยะเวลาพักสิทธิ์ต้องกำหนดเป็นค่าที่ตรวจสอบและปรับตั้งค่าได้ตามนโยบายของสถานศึกษา

## 2.5 สมมติฐานและสิ่งที่ต้องพึ่งพา (Assumptions and Dependencies)

-   นักศึกษาและเจ้าหน้าที่มีบัญชีผู้ใช้ที่ระบบยอมรับ
-   ข้อมูลอุปกรณ์และจำนวนตั้งต้นถูกบันทึกอย่างถูกต้อง
-   เจ้าหน้าที่ตรวจสอบตัวตนและสภาพอุปกรณ์ก่อนยืนยันการส่งมอบหรือรับคืน
-   ระบบสามารถเชื่อมต่อฐานข้อมูลและบริการส่งอีเมลได้เมื่อจำเป็น
-   ผู้รับผิดชอบโครงการเป็นผู้ยืนยันกฎการยืม--คืนและบทลงโทษก่อนใช้งานจริง

# 3. ข้อกำหนดด้านการทำงาน (Functional Requirements)

ข้อกำหนดต่อไปนี้ใช้รหัส FR เพื่อให้เชื่อมโยงกับ Use Case และ Test Case ได้
สถานะการพัฒนาแต่ละรายการต้องตรวจสอบจากโค้ดจริง

## 3.1 บัญชีผู้ใช้และการยืนยันตัวตน

### FR-01 การเข้าสู่ระบบ

ระบบต้องอนุญาตให้ผู้ใช้เข้าสู่ระบบด้วยอีเมลและรหัสผ่านที่ถูกต้อง
และต้องปฏิเสธข้อมูลที่ไม่ถูกต้องโดยแสดงข้อความที่เหมาะสม

### FR-02 การออกจากระบบ

ระบบต้องอนุญาตให้ผู้ใช้สิ้นสุดเซสชันของตน
และไม่อนุญาตให้ใช้เซสชันที่สิ้นสุดแล้วเข้าถึงหน้าที่ต้องมีการยืนยันตัวตน

### FR-03 การกำหนดสิทธิ์ตามบทบาท

ระบบต้องแยกสิทธิ์ระหว่างนักศึกษาและเจ้าหน้าที่
และต้องตรวจสอบสิทธิ์ก่อนดำเนินการที่จำกัดเฉพาะบทบาท

### FR-04 การรีเซ็ตรหัสผ่าน

หากมีการเปิดใช้ฟังก์ชันนี้ ระบบต้องรองรับการร้องขอรีเซ็ตรหัสผ่านผ่านอีเมลตามขั้นตอนที่ปลอดภัย
**\[ยืนยันการมีฟังก์ชันจากโค้ด\]**

## 3.2 คลังอุปกรณ์

### FR-05 การแสดงรายการอุปกรณ์

ระบบต้องแสดงรายการอุปกรณ์พร้อมข้อมูลที่จำเป็น เช่น ชื่ออุปกรณ์ หมวดหมู่ และจำนวนคงเหลือ
เพื่อให้ผู้ใช้ตรวจสอบก่อนจอง

### FR-06 การค้นหาและกรองอุปกรณ์

ระบบต้องให้ผู้ใช้ค้นหารายการอุปกรณ์และกรองตามหมวดหมู่ได้
หากฟังก์ชันดังกล่าวอยู่ในขอบเขตการพัฒนาจริง

### FR-07 การจัดการข้อมูลอุปกรณ์

ระบบต้องอนุญาตให้เจ้าหน้าที่ที่มีสิทธิ์เพิ่ม แก้ไข และปิดใช้งานอุปกรณ์ได้
โดยต้องตรวจสอบข้อมูลก่อนบันทึก

### FR-08 การปรับจำนวนคงเหลือ

ระบบต้องปรับจำนวนคงเหลือให้สอดคล้องกับการจอง การยกเลิก การส่งมอบ และการคืน
โดยป้องกันการเปลี่ยนแปลงพร้อมกันที่ทำให้จำนวนไม่ถูกต้อง

## 3.3 การจองอุปกรณ์

### FR-09 การสร้างการจอง

ระบบต้องให้นักศึกษาที่มีสิทธิ์เลือกอุปกรณ์และระบุวันที่เริ่มยืมกับวันที่คืน
จากนั้นตรวจสอบความพร้อมและเงื่อนไขก่อนบันทึกการจอง

### FR-10 การตรวจสอบจำนวนและช่วงเวลา

ก่อนยืนยันการจอง ระบบต้องตรวจสอบว่ามีจำนวนอุปกรณ์เพียงพอในช่วงเวลาที่ร้องขอ
และต้องป้องกันไม่ให้การจองพร้อมกันทำให้มีการจองเกินจำนวนที่มีอยู่

### FR-11 การสร้างหมายเลขการจองและ QR Code

เมื่อบันทึกการจองสำเร็จ ระบบต้องสร้างรหัสอ้างอิงที่ไม่ซ้ำกัน และสร้าง QR Code
ที่เชื่อมโยงกับรายการจองนั้น หาก QR Code เป็นส่วนหนึ่งของรุ่นระบบที่ส่งมอบ

### FR-12 การกำหนดเวลาหมดอายุการจอง

ระบบต้องกำหนดเวลาที่ผู้จองต้องมารับอุปกรณ์ตามค่าที่โครงการกำหนด
และต้องระบุเวลาหมดอายุให้ผู้ใช้ทราบ

### FR-13 การยกเลิกการจองโดยนักศึกษา

ระบบต้องอนุญาตให้นักศึกษายกเลิกการจองของตนได้เมื่อรายการยังอยู่ในสถานะที่อนุญาตให้ยกเลิก
และต้องปรับจำนวนคงเหลือกลับอย่างถูกต้อง

### FR-14 การยกเลิกการจองอัตโนมัติกรณีไม่มารับ

เมื่อการจองหมดอายุและยังไม่มีการยืนยันส่งมอบ ระบบต้องยกเลิกการจองตามกฎที่กำหนด
คืนจำนวนอุปกรณ์ให้คลัง และแจ้งผู้จองตามช่องทางที่รองรับ

### FR-15 การป้องกันการจองโดยผู้ถูกพักสิทธิ์

ระบบต้องปฏิเสธการจองใหม่ของบัญชีที่อยู่ระหว่างพักสิทธิ์
พร้อมแสดงวันที่หรือเงื่อนไขที่สามารถกลับมาจองได้ หากมีข้อมูลดังกล่าว

## 3.4 การส่งมอบอุปกรณ์

### FR-16 การค้นหารายการจอง

ระบบต้องให้เจ้าหน้าที่ค้นหารายการจองด้วย QR Code หรือข้อมูลอ้างอิงที่ระบบรองรับ
และแสดงรายละเอียดกับสถานะปัจจุบัน

### FR-17 การยืนยันส่งมอบ

ระบบต้องอนุญาตให้เจ้าหน้าที่ตรวจสอบสถานะการจองและยืนยันการส่งมอบด้วยตนเอง การสแกน
QR Code เพียงอย่างเดียวต้องไม่เปลี่ยนสถานะเป็นกำลังยืม

### FR-18 การบันทึกสภาพก่อนส่งมอบ

ระบบต้องให้เจ้าหน้าที่บันทึกผลการตรวจสภาพอุปกรณ์ก่อนส่งมอบ
และบันทึกรายละเอียดตำหนิได้เมื่อจำเป็น หากฟังก์ชันนี้อยู่ในรุ่นที่พัฒนา

## 3.5 การคืนอุปกรณ์และการคืนล่าช้า

### FR-19 การค้นหารายการเพื่อรับคืน

ระบบต้องให้เจ้าหน้าที่ค้นหารายการยืมที่ยังไม่ปิดรายการเพื่อดำเนินการรับคืน

### FR-20 การยืนยันรับคืน

ระบบต้องให้เจ้าหน้าที่ตรวจสอบและยืนยันการรับคืน
พร้อมบันทึกวันที่และเวลาคืนจริงตามความสามารถของระบบ

### FR-21 การบันทึกสภาพหลังคืน

ระบบต้องให้เจ้าหน้าที่บันทึกสภาพอุปกรณ์หลังคืน
และสามารถระบุอุปกรณ์ที่ชำรุดเพื่อเปลี่ยนเป็นสถานะปิดใช้งานหรือรอซ่อมได้ตามกฎของระบบ

### FR-22 การคำนวณการคืนล่าช้า

เมื่อยืนยันการคืน ระบบต้องเปรียบเทียบวันคืนจริงกับวันครบกำหนด
และระบุว่าคืนตรงเวลาหรือเกินกำหนด

### FR-23 การพักสิทธิ์ตามเงื่อนไข

หากการคืนเข้าเกณฑ์บทลงโทษ ระบบต้องกำหนดช่วงเวลาพักสิทธิ์การจองตามค่าที่ได้รับอนุมัติ
และต้องแสดงสถานะกับวันที่สิ้นสุดการพักสิทธิ์อย่างชัดเจน

### FR-24 การปลดพักสิทธิ์

ระบบต้องคืนสิทธิ์การจองโดยอัตโนมัติเมื่อครบกำหนด
หรือให้เจ้าหน้าที่ผู้มีสิทธิ์ปลดพักสิทธิ์เป็นกรณีพิเศษได้ หากนโยบายและระบบรองรับ

## 3.6 การแจ้งเตือน

### FR-25 การแจ้งยืนยันการจอง

เมื่อการจองสำเร็จ ระบบควรส่งอีเมลยืนยัน พร้อมรายละเอียดการจอง เวลาที่ต้องมารับ และ QR
Code หากรองรับ

### FR-26 การแจ้งเตือนกำหนดคืน

ระบบต้องส่งการแจ้งเตือนก่อนถึงกำหนดและในวันครบกำหนดตามนโยบายที่กำหนด
โดยต้องไม่ส่งการแจ้งเตือนซ้ำเกินกว่ากฎที่ตั้งไว้

### FR-27 การแจ้งเตือนรายการเกินกำหนด

ระบบต้องตรวจหารายการที่เกินกำหนดและส่งการแจ้งเตือนตามรอบที่กำหนดจนกว่าจะมีการคืนหรือปิดรายการ

### FR-28 การแจ้งเตือนยกเลิกและคืนสำเร็จ

ระบบควรส่งอีเมลแจ้งผู้ใช้เมื่อรายการจองถูกยกเลิกอัตโนมัติ และเมื่อการคืนได้รับการยืนยันสำเร็จ

## 3.7 ประวัติและแดชบอร์ด

### FR-29 ประวัติการยืมของนักศึกษา

ระบบต้องให้นักศึกษาดูรายการจองและประวัติการยืม--คืนของตนเอง
พร้อมแสดงสถานะของแต่ละรายการ

### FR-30 แดชบอร์ดเจ้าหน้าที่

ระบบควรแสดงข้อมูลสรุปที่ช่วยให้เจ้าหน้าที่ติดตามงาน เช่น จำนวนรายการที่กำลังยืม
รายการเกินกำหนด และบัญชีที่ถูกพักสิทธิ์

### FR-31 การดูแลข้อมูลส่วนบุคคล

ระบบต้องแสดงข้อมูลผู้ใช้และประวัติการยืมให้เฉพาะผู้ใช้ที่มีสิทธิ์เข้าถึงข้อมูลนั้น

# 4. ข้อกำหนดที่ไม่ใช่ด้านการทำงาน (Non-functional Requirements)

ข้อกำหนด NFR ด้านล่างเป็นเป้าหมายที่เสนอไว้
ต้องปรับตามศักยภาพของระบบและเกณฑ์ที่ผู้สอนหรือผู้รับผิดชอบอนุมัติ

## 4.1 ความปลอดภัย (Security)

-   **NFR-01:** ระบบต้องตรวจสอบสิทธิ์ของผู้ใช้ก่อนอนุญาตให้เข้าถึงฟังก์ชันที่จำกัดตามบทบาท
-   **NFR-02:**
    ระบบต้องป้องกันไม่ให้นักศึกษาแก้ไขหรือยืนยันการส่งมอบและรับคืนแทนเจ้าหน้าที่
-   **NFR-03:** รหัสผ่านและข้อมูลรับรองต้องไม่ถูกเก็บในรูปแบบข้อความธรรมดา
    และต้องใช้กลไกที่ปลอดภัยตามเทคโนโลยีที่เลือก
-   **NFR-04:** ข้อมูลลับ เช่น รหัสผ่านบริการและคีย์ลับ ต้องไม่ถูก commit ลง
    Repository
-   **NFR-05:** ระบบควรตรวจสอบและทำความสะอาดข้อมูลนำเข้าก่อนประมวลผล
    เพื่อป้องกันข้อมูลผิดรูปแบบและการโจมตีที่เกี่ยวข้อง
-   **NFR-06:** การเชื่อมต่อที่ใช้ในสภาพแวดล้อมจริงควรใช้ HTTPS

## 4.2 ประสิทธิภาพ (Performance)

-   **NFR-07:**
    การแสดงรายการอุปกรณ์และจำนวนคงเหลือต้องอยู่ในเกณฑ์เวลาตอบสนองที่ทีมกำหนดและทดสอบได้
    **\[กำหนดค่าตัวเลขหลังทดสอบ\]**
-   **NFR-08:**
    การตรวจสอบจำนวนคงเหลือและบันทึกการจองต้องทำงานโดยไม่ทำให้เกิดการจองเกินจำนวน
-   **NFR-09:** งานแจ้งเตือนตามกำหนดเวลาต้องทำงานตามรอบที่กำหนด
    และต้องจัดการกรณีส่งไม่สำเร็จได้อย่างเหมาะสม

## 4.3 ความถูกต้องและความสอดคล้องของข้อมูล (Data Integrity)

-   **NFR-10:** จำนวนอุปกรณ์คงเหลือต้องไม่ติดลบ
-   **NFR-11:** การจอง การยกเลิก การส่งมอบ
    และการคืนต้องเปลี่ยนสถานะและจำนวนคงเหลืออย่างสอดคล้องกัน
-   **NFR-12:**
    ระบบต้องป้องกันการยืนยันซ้ำสำหรับรายการที่ปิดแล้วหรือไม่อยู่ในสถานะที่ถูกต้อง
-   **NFR-13:** ข้อมูลการยืมและคืนต้องสามารถตรวจสอบย้อนหลังได้ตามสิทธิ์

## 4.4 การใช้งาน (Usability)

-   **NFR-14:** หน้าจอควรใช้ข้อความภาษาไทยที่เข้าใจง่ายและสอดคล้องกัน
-   **NFR-15:** ระบบควรแสดงข้อความเมื่อดำเนินการสำเร็จหรือเกิดข้อผิดพลาด
    โดยไม่เปิดเผยข้อมูลลับ
-   **NFR-16:** หน้าจอควรรองรับขนาดหน้าจอที่ใช้กันทั่วไป ทั้งคอมพิวเตอร์และโทรศัพท์มือถือ
    หากอยู่ในขอบเขตโครงการ

## 4.5 การบำรุงรักษาและการสำรองข้อมูล (Maintainability and Backup)

-   **NFR-17:** โค้ดควรแบ่งส่วนตามหน้าที่และมีชื่อไฟล์/ฟังก์ชันที่สื่อความหมาย
-   **NFR-18:** การเปลี่ยนแปลงข้อกำหนดสำคัญควรบันทึกผ่านระบบควบคุมเวอร์ชัน Git
-   **NFR-19:**
    ควรกำหนดวิธีสำรองและกู้คืนฐานข้อมูลตามความเหมาะสมกับสภาพแวดล้อมที่ใช้งานจริง

# 5. กฎทางธุรกิจและสถานะ (Business Rules and States)

## 5.1 กฎทางธุรกิจ (Business Rules)

-   **BR-01:** เฉพาะผู้ใช้ที่มีสถานะบัญชีปกติเท่านั้นที่สามารถสร้างการจองใหม่ได้
-   **BR-02:** การจองต้องผ่านการตรวจสอบจำนวนคงเหลือและช่วงเวลาที่ขอยืม
-   **BR-03:** การยกเลิกการจองที่ยังไม่ส่งมอบต้องคืนจำนวนอุปกรณ์ให้คลังอย่างถูกต้อง
-   **BR-04:**
    การหมดอายุการจองโดยไม่มารับต้องทำให้รายการถูกยกเลิกและคืนจำนวนอุปกรณ์ตามนโยบาย
-   **BR-05:** การสแกน QR Code เป็นการค้นหารายการเท่านั้น
    การส่งมอบต้องรอเจ้าหน้าที่กดยืนยัน
-   **BR-06:** การรับคืนต้องผ่านการยืนยันจากเจ้าหน้าที่
-   **BR-07:** เมื่อคืนอุปกรณ์ ต้องตรวจสอบวันคืนจริงเทียบกับวันครบกำหนด
-   **BR-08:** การพักสิทธิ์ต้องจำกัดเฉพาะการจองใหม่ หากเป็นไปตามนโยบายที่ระบุใน
    README
-   **BR-09:** อุปกรณ์ที่ชำรุดหรือส่งซ่อมต้องไม่ถูกนับเป็นอุปกรณ์พร้อมให้ยืม
-   **BR-10:** การเปลี่ยนแปลงสถานะทุกครั้งต้องทำให้ข้อมูลจำนวนคงเหลือสอดคล้องกัน

# 6. ข้อกำหนดด้านข้อมูล (Data Requirements)

                                      และผลการส่ง หากระบบเก็บข้อมูลนี้

  การพักสิทธิ์                            ผู้ใช้ เหตุผล วันที่เริ่มและสิ้นสุด
                                      และผู้ดำเนินการ หากมี
  -----------------------------------------------------------------------

ตารางนี้เป็นข้อกำหนดเชิงข้อมูลระดับแนวคิด ไม่ใช่รายชื่อและคอลัมน์ของฐานข้อมูลจริง
ต้องตรวจสอบกับไฟล์ใน `db/` ก่อนจัดทำ Data Dictionary และ ER Diagram

## 6.2 ความถูกต้องของข้อมูล

1.  รหัสรายการหลักต้องไม่ซ้ำกัน
2.  การจองต้องอ้างอิงผู้ใช้และอุปกรณ์ที่มีอยู่จริง
3.  วันที่เริ่มยืมและวันกำหนดคืนต้องเป็นไปตามกฎที่กำหนด
4.  จำนวนคงเหลือต้องไม่ต่ำกว่าศูนย์
5.  รายการที่คืนแล้วหรือยกเลิกแล้วต้องไม่ถูกยืนยันซ้ำในลักษณะที่ทำให้ข้อมูลผิดพลาด
6.  ข้อมูลส่วนบุคคลต้องแสดงเท่าที่จำเป็นและตามสิทธิ์ของผู้ใช้

# 7. ส่วนติดต่อผู้ใช้และการเชื่อมต่อภายนอก (Interfaces)

## 7.1 ส่วนติดต่อผู้ใช้ (User Interface)

ระบบควรมีหน้าจอหลักตามบทบาทและฟังก์ชันที่ส่งมอบจริง ได้แก่: - หน้าเข้าสู่ระบบ -
หน้ารายการอุปกรณ์และรายละเอียดอุปกรณ์ - หน้าสร้างและดูการจอง -
หน้าประวัติการยืมของนักศึกษา -
หน้าสำหรับเจ้าหน้าที่ค้นหา/สแกนรายการและยืนยันส่งมอบหรือรับคืน - หน้าจัดการอุปกรณ์ -
หน้าแดชบอร์ดเจ้าหน้าที่ - หน้าหรือส่วนแสดงการแจ้งเตือนและสถานะพักสิทธิ์

## 7.2 การเชื่อมต่อฐานข้อมูล

ระบบต้องอ่านและบันทึกข้อมูลผ่านกลไกที่กำหนดในโครงการ
และต้องจัดการข้อผิดพลาดเมื่อไม่สามารถเชื่อมต่อหรือบันทึกข้อมูลได้
รายละเอียดชนิดฐานข้อมูลและโครงสร้างตารางให้ยึดจากไฟล์ตั้งค่าและสคริปต์ฐานข้อมูลจริง

## 7.3 การเชื่อมต่ออีเมล

หากเปิดใช้การแจ้งเตือนทางอีเมล ระบบต้องใช้การตั้งค่าบริการอีเมลที่เหมาะสม
และต้องไม่เปิดเผยข้อมูลรับรองในโค้ดหรือ Repository

## 7.4 QR Code

QR Code ต้องอ้างอิงรายการจองที่ถูกต้อง และการเปิดหรือสแกน QR Code
ต้องไม่ทำให้สถานะการยืมเปลี่ยนโดยอัตโนมัติ
ต้องมีการตรวจสอบสถานะและยืนยันโดยเจ้าหน้าที่ก่อนส่งมอบหรือรับคืน

# 8. เกณฑ์การยอมรับระบบ (Acceptance Criteria)

เกณฑ์ต่อไปนี้ใช้เป็นแนวทางในการทดสอบ ต้องปรับให้ตรงกับฟังก์ชันที่พัฒนาเสร็จจริง

  -----------------------------------------------------------------------------------------------
  รหัสทดสอบเบื้องต้น          สถานการณ์                      ผลลัพธ์ที่คาดหวัง
  ----------------------- ----------------------------- -----------------------------------------
  AC-01                   เข้าสู่ระบบด้วยข้อมูลถูกต้อง          ผู้ใช้เข้าสู่ระบบและเห็นฟังก์ชันตามสิทธิ์

  AC-02                   เข้าสู่ระบบด้วยข้อมูลผิด             ระบบปฏิเสธและแสดงข้อความที่เหมาะสม

  AC-03                   จองอุปกรณ์ที่มีจำนวนพร้อมใช้         ระบบสร้างรายการจองและปรับจำนวนอย่างถูกต้อง

  AC-04                   จองอุปกรณ์ที่ไม่มีจำนวนพร้อมใช้       ระบบไม่สร้างการจองที่เกินจำนวน

  AC-05                   ผู้ใช้ที่ถูกพักสิทธิ์พยายามจอง          ระบบปฏิเสธการจองใหม่

  AC-06                   นักศึกษายกเลิกการจองที่ยังไม่ส่งมอบ   ระบบยกเลิกและคืนจำนวนอุปกรณ์อย่างถูกต้อง

  AC-07                   สแกน QR Code สำหรับรายการรอรับ  ระบบแสดงรายละเอียด
                                                        แต่ไม่เปลี่ยนเป็นกำลังยืมจนกว่าเจ้าหน้าที่จะยืนยัน

  AC-08                   เจ้าหน้าที่ยืนยันส่งมอบ              สถานะการจองและอุปกรณ์เปลี่ยนตามกฎ

  AC-09                   เจ้าหน้าที่ยืนยันรับคืน               ระบบบันทึกการคืนและปรับสถานะ/จำนวนอย่างถูกต้อง

  AC-10                   คืนอุปกรณ์หลังวันครบกำหนด          ระบบระบุการคืนล่าช้าและใช้กฎพักสิทธิ์ที่ได้รับอนุมัติ

  AC-11                   การจองหมดอายุโดยไม่มารับ         ระบบยกเลิกตามกฎและคืนจำนวนอุปกรณ์

  AC-12                   ผู้ใช้พยายามเข้าถึงฟังก์ชันที่ไม่มีสิทธิ์    ระบบปฏิเสธการเข้าถึง

  AC-13                   อีเมลแจ้งเตือนส่งไม่สำเร็จ          ระบบจัดการข้อผิดพลาดตามแนวทางที่ออกแบบ
                                                        และไม่รายงานว่าส่งสำเร็จทั้งที่ไม่สำเร็จ
  -----------------------------------------------------------------------------------------------

การทดสอบแต่ละข้อควรบันทึกข้อมูลทดสอบ ขั้นตอน ผลที่คาดหวัง ผลที่เกิดขึ้นจริง
และสถานะผ่าน/ไม่ผ่านไว้ในเอกสาร Test Case หรือ Test Report แยกต่างหาก

# 9. ประเด็นที่ต้องตรวจสอบก่อนอนุมัติ SRS

รายการต่อไปนี้ต้องตรวจสอบกับโค้ดและผู้เกี่ยวข้องก่อนเปลี่ยนสถานะเอกสารจากร่างเป็นฉบับสมบูรณ์:

-   [ ] โครงสร้างจริงของ Frontend และ Backend
-   [ ] ชนิดฐานข้อมูลและ schema ที่ใช้งานจริง
-   [ ] วิธีเข้าสู่ระบบและการแบ่งสิทธิ์
-   [ ] ฟังก์ชัน QR Code มีการพัฒนาและทำงานอย่างไร
-   [ ] วิธีจัดการจำนวนอุปกรณ์และป้องกันการจองซ้อน
-   [ ] งานอัตโนมัติสำหรับหมดอายุการจองและแจ้งเตือน
-   [ ] กฎการคืนล่าช้าและระยะเวลาพักสิทธิ์ที่ได้รับอนุมัติ
-   [ ] รูปแบบและความถี่ของอีเมลแจ้งเตือน
-   [ ] เกณฑ์ประสิทธิภาพที่สามารถทดสอบได้
-   [ ] ข้อกำหนดเพิ่มเติมจากอาจารย์หรือรายวิชา
-   [ ] ผลการทดสอบที่ยืนยันว่าแต่ละข้อกำหนดทำงานได้จริง
