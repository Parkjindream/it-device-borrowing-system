# 1. บทนำ (Introduction)

## 1.1 วัตถุประสงค์ของเอกสาร (Purpose)

เอกสารฉบับนี้จัดทำขึ้นเพื่ออธิบายว่าระบบยืม–คืนอุปกรณ์ไอทีควรทำอะไรได้บ้าง ใครเป็นผู้ใช้งาน และระบบควรทำงานอย่างไร เพื่อให้สมาชิกในทีมเข้าใจตรงกันก่อนนำไปออกแบบและพัฒนาระบบจริง

นอกจากนี้ เอกสารยังใช้เป็นแนวทางในการตรวจสอบว่าระบบที่พัฒนาขึ้นสามารถตอบโจทย์การใช้งานได้ตามที่วางแผนไว้หรือไม่ เช่น นักศึกษาสามารถจองอุปกรณ์ได้จริงหรือไม่ เจ้าหน้าที่สามารถบันทึกการรับคืนได้หรือไม่ และข้อมูลที่ระบบแสดงมีความถูกต้องเพียงใด

## 1.2 ขอบเขตของระบบ (Scope)

ระบบยืม–คืนอุปกรณ์ไอทีเป็นเว็บแอปพลิเคชันที่พัฒนาขึ้นเพื่อช่วยให้การยืมและคืนอุปกรณ์ภายในสถานศึกษาสะดวกขึ้น นักศึกษาสามารถเข้ามาดูอุปกรณ์ที่มีให้ยืม ตรวจสอบจำนวนที่พร้อมใช้งาน และทำรายการจองได้โดยไม่ต้องเสียเวลาสอบถามเจ้าหน้าที่ทุกครั้ง

ในส่วนของเจ้าหน้าที่ ระบบจะช่วยให้จัดการข้อมูลอุปกรณ์ ตรวจสอบรายการจอง บันทึกการส่งมอบและรับคืน รวมถึงติดตามอุปกรณ์ที่ยังไม่ได้คืนตามกำหนดได้ง่ายขึ้น

ความสามารถที่กำหนดไว้ในร่างนี้ประกอบด้วย

1. **การเข้าสู่ระบบ:** ผู้ใช้เข้าสู่ระบบด้วยอีเมลและรหัสผ่าน
2. **การกำหนดสิทธิ์:** ระบบแยกการใช้งานระหว่างนักศึกษาและเจ้าหน้าที่
3. **การดูรายการอุปกรณ์:** ผู้ใช้สามารถดูรายละเอียดและจำนวนอุปกรณ์ที่พร้อมให้ยืม
4. **การค้นหาอุปกรณ์:** ผู้ใช้สามารถค้นหาหรือกรองรายการอุปกรณ์ตามความต้องการ หากมีฟังก์ชันนี้ในระบบจริง
5. **การจองอุปกรณ์:** นักศึกษาสามารถเลือกอุปกรณ์และระบุวันที่ต้องการยืมกับวันที่ต้องการคืน
6. **การยกเลิกการจอง:** นักศึกษาสามารถยกเลิกรายการที่ยังอยู่ในสถานะที่อนุญาต
7. **การใช้ QR Code:** ระบบสามารถสร้างหรือใช้ QR Code เพื่อช่วยค้นหารายการจอง หากมีการพัฒนาความสามารถนี้
8. **การส่งมอบอุปกรณ์:** เจ้าหน้าที่ตรวจสอบรายการและยืนยันการส่งมอบให้ผู้ยืม
9. **การรับคืนอุปกรณ์:** เจ้าหน้าที่บันทึกการคืนและตรวจสอบสภาพอุปกรณ์
10. **การติดตามการคืนล่าช้า:** ระบบช่วยตรวจสอบรายการที่เลยกำหนดคืน
11. **การแจ้งเตือน:** ระบบอาจส่งอีเมลแจ้งผลการจองหรือเตือนเกี่ยวกับกำหนดคืน
12. **การดูประวัติ:** นักศึกษาสามารถตรวจสอบประวัติการจองและการยืมของตนเอง
13. **การดูภาพรวม:** เจ้าหน้าที่สามารถดูข้อมูลสรุปเกี่ยวกับอุปกรณ์และรายการยืม–คืนได้ หากระบบรองรับ

รายการข้างต้นเป็นขอบเขตที่เสนอไว้สำหรับระบบ ไม่ได้หมายความว่าทุกฟังก์ชันได้รับการพัฒนาเสร็จแล้ว จึงต้องตรวจสอบกับโค้ดจริงอีกครั้งก่อนสรุปว่าแต่ละฟังก์ชันใช้งานได้

## 1.3 ปัญหาและเหตุผลในการพัฒนาระบบ

การยืม–คืนอุปกรณ์ในสถานศึกษาอาจดูเหมือนเป็นเรื่องง่าย แต่หากไม่มีระบบช่วยจัดการ ก็อาจเกิดปัญหาได้หลายอย่าง เช่น นักศึกษาไม่ทราบว่าอุปกรณ์ที่ต้องการยังว่างอยู่หรือไม่ เจ้าหน้าที่ต้องคอยตอบคำถามเดิม ๆ หรือข้อมูลการยืมและการคืนอาจถูกบันทึกไม่ครบถ้วน

อีกปัญหาหนึ่งคือการติดตามอุปกรณ์ที่ยังไม่ได้คืน หากมีผู้ยืมหลายคน การตรวจสอบด้วยตนเองอาจทำให้เสียเวลาและมีโอกาสตกหล่นได้

ด้วยเหตุนี้ จึงมีแนวคิดที่จะพัฒนาระบบยืม–คืนอุปกรณ์ไอทีขึ้นมา เพื่อรวบรวมข้อมูลไว้ในที่เดียว ช่วยให้ผู้ใช้ตรวจสอบข้อมูลได้สะดวกขึ้น และช่วยให้เจ้าหน้าที่ติดตามรายการต่าง ๆ ได้เป็นระบบมากกว่าเดิม

ในช่วงท้ายจะกล่าวถึงเกณฑ์ที่ใช้ตรวจสอบว่าระบบทำงานได้ตามที่กำหนดหรือไม่ รวมถึงรายการที่ยังต้องตรวจสอบก่อนนำเอกสารไปใช้เป็นฉบับสมบูรณ์

# 2. รายละเอียดโดยรวมของระบบ (Overall Description)

## 2.1 ภาพรวมของผลิตภัณฑ์ (Product Perspective)

ระบบนี้ถูกออกแบบให้เป็นเว็บแอปพลิเคชันที่ช่วยจัดการงานยืม–คืนอุปกรณ์ไอที โดยมีส่วนที่ผู้ใช้มองเห็นและใช้งาน ส่วนที่ประมวลผลคำสั่งต่าง ๆ และส่วนที่จัดเก็บข้อมูลของระบบ

ตัวอย่างเช่น เมื่อนักศึกษาจองอุปกรณ์ ระบบควรตรวจสอบก่อนว่าอุปกรณ์ยังมีจำนวนเพียงพอหรือไม่ หากจองสำเร็จ ข้อมูลการจองก็ต้องถูกบันทึกไว้ เพื่อให้เจ้าหน้าที่สามารถตรวจสอบและดำเนินการส่งมอบอุปกรณ์ได้ในภายหลัง

อย่างไรก็ตาม เทคโนโลยีที่ใช้จริง เช่น ภาษาโปรแกรม เฟรมเวิร์ก และชนิดฐานข้อมูล จะต้องตรวจสอบจากไฟล์ของโครงการก่อนนำมาเขียนเป็นข้อมูลยืนยันในเอกสาร

## 2.2 กลุ่มผู้ใช้งานและสิทธิ์ (User Classes)

ระบบแบ่งผู้ใช้งานหลักออกเป็น 2 กลุ่ม เพื่อให้แต่ละคนเข้าถึงเฉพาะความสามารถที่จำเป็นต่อหน้าที่ของตน

### 2.2.1 นักศึกษา (Student)

นักศึกษาเป็นผู้ที่เข้ามาใช้งานระบบเพื่อค้นหาและจองอุปกรณ์ที่ต้องการ โดยควรสามารถทำสิ่งต่อไปนี้ได้

- เข้าสู่ระบบและออกจากระบบ
- ดูรายการอุปกรณ์และจำนวนที่พร้อมให้ยืม
- เลือกอุปกรณ์และระบุช่วงเวลาที่ต้องการยืม
- ตรวจสอบสถานะการจองของตนเอง
- ยกเลิกการจองเมื่อยังอยู่ในสถานะที่อนุญาต
- ดูประวัติการยืมและการคืนของตนเอง
- รับการแจ้งเตือนที่เกี่ยวข้อง หากระบบมีการเปิดใช้ฟังก์ชันนี้

หากระบบมีการพักสิทธิ์การยืม นักศึกษาควรสามารถตรวจสอบสถานะของตนเองได้ด้วย

### 2.2.2 เจ้าหน้าที่ (Staff)

เจ้าหน้าที่เป็นผู้ดูแลอุปกรณ์และรับผิดชอบการดำเนินการยืม–คืน จึงควรสามารถทำงานต่อไปนี้ได้

- ดูและจัดการข้อมูลอุปกรณ์
- ตรวจสอบรายการจองของนักศึกษา
- ค้นหารายการจองด้วยรหัสอ้างอิงหรือ QR Code หากระบบรองรับ
- ตรวจสอบข้อมูลก่อนส่งมอบอุปกรณ์
- ยืนยันการส่งมอบอุปกรณ์ให้ผู้ยืม
- บันทึกการรับคืนและตรวจสอบสภาพอุปกรณ์
- ติดตามรายการที่ยังไม่คืนตามกำหนด
- ดูข้อมูลภาพรวมของการยืม–คืน
- จัดการสถานะการพักสิทธิ์ตามอำนาจที่ได้รับอนุญาต หากระบบรองรับ

## 2.3 สภาพแวดล้อมในการใช้งาน (Operating Environment)

ผู้ใช้จะเข้าถึงระบบผ่านเว็บเบราว์เซอร์บนอุปกรณ์ที่รองรับ โดยระบบต้องสามารถติดต่อกับส่วนประมวลผลและฐานข้อมูลเพื่อเรียกดูหรือบันทึกข้อมูลได้

หากมีการส่งอีเมลแจ้งเตือน ระบบต้องเชื่อมต่อกับบริการอีเมลที่ตั้งค่าไว้ถูกต้อง ส่วนการสร้างและสแกน QR Code ต้องรองรับวิธีการใช้งานที่โครงการเลือกใช้

รายละเอียดเกี่ยวกับเบราว์เซอร์ ระบบปฏิบัติการ และเทคโนโลยีที่รองรับ ควรกำหนดให้ตรงกับสภาพแวดล้อมที่ใช้พัฒนาจริง

## 2.4 ข้อจำกัดของระบบ (Constraints)

เพื่อให้ข้อมูลการยืม–คืนถูกต้อง ระบบควรมีข้อจำกัดในการทำงานดังนี้

1. ระบบต้องไม่อนุญาตให้จองอุปกรณ์เกินจำนวนที่มีให้ยืม
2. จำนวนอุปกรณ์ที่พร้อมใช้งานต้องไม่ติดลบ
3. การสแกน QR Code ใช้สำหรับค้นหารายการ ไม่ใช่การยืนยันส่งมอบหรือรับคืนโดยอัตโนมัติ
4. เฉพาะเจ้าหน้าที่ที่มีสิทธิ์เท่านั้นที่สามารถยืนยันการส่งมอบและรับคืนได้
5. หากนักศึกษาถูกพักสิทธิ์ตามกฎของระบบ จะต้องไม่สามารถสร้างรายการจองใหม่ในช่วงที่ถูกพักสิทธิ์ได้
6. การยกเลิกการจอง การส่งมอบ และการรับคืนต้องปรับข้อมูลให้สอดคล้องกัน
7. ระยะเวลายืม เวลาหมดอายุการจอง และเงื่อนไขการพักสิทธิ์ต้องได้รับการยืนยันก่อนนำไปใช้งานจริง

## 2.5 สมมติฐานและสิ่งที่ระบบต้องพึ่งพา (Assumptions and Dependencies)

การทำงานของระบบอาศัยเงื่อนไขบางอย่าง เช่น นักศึกษาและเจ้าหน้าที่ต้องมีบัญชีผู้ใช้ที่ถูกต้อง ข้อมูลอุปกรณ์ต้องได้รับการบันทึกอย่างครบถ้วน และเจ้าหน้าที่ต้องตรวจสอบอุปกรณ์ก่อนส่งมอบหรือรับคืน

นอกจากนี้ หากระบบใช้บริการอีเมลหรือฐานข้อมูลภายนอก บริการเหล่านั้นต้องสามารถใช้งานได้ด้วย หากเกิดปัญหาการเชื่อมต่อ ระบบควรแจ้งข้อผิดพลาดอย่างเหมาะสมแทนการแสดงผลสำเร็จทั้งที่ยังไม่ได้ดำเนินการจริง

# 3. ข้อกำหนดด้านการทำงาน (Functional Requirements)

บทนี้อธิบายความสามารถที่ระบบควรมี โดยแต่ละข้อจะมีรหัส FR เพื่อให้ทีมพัฒนาสามารถนำไปใช้ตรวจสอบกับโค้ดและสร้างกรณีทดสอบได้ง่ายขึ้น

ข้อกำหนดเหล่านี้เป็นสิ่งที่ระบบควรทำได้ตามขอบเขตโครงการ ส่วนสถานะการพัฒนาจริงต้องตรวจสอบจากระบบที่มีอยู่

## 3.1 บัญชีผู้ใช้และการเข้าสู่ระบบ

ก่อนที่ผู้ใช้จะจองอุปกรณ์หรือเข้าถึงข้อมูลส่วนตัว ระบบจำเป็นต้องตรวจสอบก่อนว่าผู้ใช้เป็นใคร และมีสิทธิ์ทำอะไรได้บ้าง

### FR-01 การเข้าสู่ระบบ

ระบบต้องให้ผู้ใช้เข้าสู่ระบบด้วยอีเมลและรหัสผ่านที่ถูกต้อง หากข้อมูลไม่ถูกต้อง ระบบควรปฏิเสธการเข้าสู่ระบบและแสดงข้อความที่เข้าใจง่าย เพื่อให้ผู้ใช้ทราบว่าต้องแก้ไขข้อมูลอย่างไร

### FR-02 การออกจากระบบ

เมื่อผู้ใช้ต้องการออกจากระบบ ผู้ใช้ควรสามารถออกจากระบบได้อย่างสะดวก และระบบต้องไม่อนุญาตให้ใช้เซสชันที่สิ้นสุดแล้วเข้าถึงหน้าที่ต้องเข้าสู่ระบบอีกครั้ง

### FR-03 การแบ่งสิทธิ์ผู้ใช้งาน

นักศึกษาและเจ้าหน้าที่มีหน้าที่แตกต่างกัน ระบบจึงต้องแยกสิทธิ์ให้ชัดเจน เช่น นักศึกษาสามารถจองอุปกรณ์ของตนเองได้ แต่ไม่ควรเข้าถึงหน้าจัดการข้อมูลอุปกรณ์สำหรับเจ้าหน้าที่

ระบบต้องตรวจสอบสิทธิ์ก่อนดำเนินการ ไม่ใช่เพียงซ่อนปุ่มที่ผู้ใช้ไม่มีสิทธิ์กด

### FR-04 การรีเซ็ตรหัสผ่าน

หากระบบมีฟังก์ชันรีเซ็ตรหัสผ่าน ผู้ใช้ควรสามารถร้องขอเปลี่ยนรหัสผ่านผ่านขั้นตอนที่ปลอดภัยได้ ทั้งนี้ต้องตรวจสอบก่อนว่าฟังก์ชันดังกล่าวมีอยู่ในระบบจริงหรือไม่

## 3.2 การดูและจัดการข้อมูลอุปกรณ์

นักศึกษาควรทราบก่อนว่ามีอุปกรณ์อะไรให้ยืมบ้าง ส่วนเจ้าหน้าที่ต้องสามารถดูแลข้อมูลเหล่านั้นได้ เพื่อให้ข้อมูลที่แสดงต่อผู้ใช้ตรงกับสถานการณ์จริง

### FR-05 การแสดงรายการอุปกรณ์

ระบบต้องแสดงรายการอุปกรณ์ที่มีอยู่ โดยให้ข้อมูลที่จำเป็น เช่น ชื่ออุปกรณ์ ประเภท และจำนวนที่พร้อมให้ยืม เพื่อช่วยให้นักศึกษาตัดสินใจได้ว่าจะเลือกอุปกรณ์ใด

### FR-06 การค้นหาและกรองอุปกรณ์

ระบบควรช่วยให้ผู้ใช้ค้นหาอุปกรณ์ได้สะดวกขึ้น เช่น ค้นหาจากชื่อหรือเลือกดูเฉพาะอุปกรณ์ในหมวดหมู่ที่สนใจ หากโครงการมีฟังก์ชันนี้

### FR-07 การจัดการข้อมูลอุปกรณ์

เจ้าหน้าที่ที่ได้รับอนุญาตควรสามารถเพิ่มข้อมูลอุปกรณ์ แก้ไขรายละเอียด และปิดใช้งานอุปกรณ์ที่ไม่พร้อมให้ยืมได้

ก่อนบันทึกข้อมูล ระบบควรตรวจสอบความถูกต้องของข้อมูล เพื่อป้องกันข้อมูลที่ไม่ครบถ้วนหรือไม่สมเหตุสมผล

### FR-08 การปรับจำนวนอุปกรณ์คงเหลือ

เมื่อมีการจอง การยกเลิก การส่งมอบ หรือการรับคืน จำนวนอุปกรณ์ที่พร้อมให้ยืมต้องเปลี่ยนแปลงตามกฎของระบบ

ตัวอย่างเช่น หากอุปกรณ์มีจำนวนพร้อมให้ยืมเพียงหนึ่งชิ้น และมีผู้จองสำเร็จแล้ว ระบบต้องไม่แสดงว่าอุปกรณ์ชิ้นเดิมยังพร้อมให้ผู้ใช้อีกคนจองได้ในช่วงเวลาเดียวกัน

## 3.3 การจองอุปกรณ์

การจองเป็นส่วนสำคัญของระบบ เพราะช่วยให้นักศึกษาวางแผนการใช้อุปกรณ์ล่วงหน้าได้ แต่ระบบต้องตรวจสอบจำนวนและช่วงเวลาให้ถูกต้อง เพื่อไม่ให้เกิดปัญหาจองอุปกรณ์ชิ้นเดียวกันเกินจำนวนที่มีอยู่

### FR-09 การสร้างรายการจอง

นักศึกษาที่มีสิทธิ์ควรสามารถเลือกอุปกรณ์ที่ต้องการ ระบุวันที่เริ่มยืมและวันที่กำหนดคืน แล้วส่งคำขอจองผ่านระบบได้

ก่อนบันทึกรายการ ระบบต้องตรวจสอบข้อมูลที่จำเป็นและเงื่อนไขการจองก่อน หากข้อมูลไม่ครบหรือไม่ผ่านเงื่อนไข ระบบควรแจ้งให้ผู้ใช้ทราบ

### FR-10 การตรวจสอบจำนวนและช่วงเวลาที่จอง

ก่อนยืนยันการจอง ระบบต้องตรวจสอบว่าอุปกรณ์มีจำนวนเพียงพอในช่วงเวลาที่นักศึกษาต้องการหรือไม่

หากอุปกรณ์ไม่ว่าง ระบบควรแจ้งให้ผู้ใช้ทราบแทนการสร้างรายการจองที่เกินจำนวน นอกจากนี้ ระบบต้องป้องกันกรณีที่ผู้ใช้หลายคนจองพร้อมกันจนทำให้จำนวนอุปกรณ์คลาดเคลื่อน

### FR-11 การสร้างรหัสจองและ QR Code

เมื่อจองสำเร็จ ระบบควรสร้างรหัสอ้างอิงที่ไม่ซ้ำกัน เพื่อให้ผู้ใช้และเจ้าหน้าที่สามารถค้นหารายการจองได้ง่ายขึ้น

หากระบบรองรับ QR Code ควรสร้าง QR Code ที่เชื่อมโยงกับรายการจองนั้นด้วย เพื่อช่วยลดเวลาในการค้นหาข้อมูลขณะรับหรือคืนอุปกรณ์

### FR-12 การกำหนดเวลาหมดอายุการจอง

หากระบบกำหนดให้ผู้จองต้องมารับอุปกรณ์ภายในเวลาที่กำหนด ระบบควรแสดงเวลาหมดอายุให้ผู้ใช้ทราบอย่างชัดเจน

เมื่อเลยกำหนด ระบบควรดำเนินการตามกฎที่โครงการอนุมัติ เช่น ยกเลิกรายการจองและคืนจำนวนอุปกรณ์ให้พร้อมใช้งาน โดยต้องตรวจสอบว่ากระบวนการนี้ได้รับการพัฒนาไว้จริงหรือไม่

### FR-13 การยกเลิกการจองโดยนักศึกษา

นักศึกษาควรสามารถยกเลิกการจองของตนเองได้ หากรายการยังอยู่ในสถานะที่อนุญาตให้ยกเลิก

เมื่อยกเลิกสำเร็จ ระบบต้องปรับสถานะและจำนวนอุปกรณ์ให้ถูกต้อง เพื่อให้อุปกรณ์กลับมาพร้อมให้ผู้ใช้คนอื่นจองได้ตามเงื่อนไขของระบบ

### FR-14 การยกเลิกการจองเมื่อผู้ใช้ไม่มารับอุปกรณ์

หากผู้จองไม่มารับอุปกรณ์ภายในเวลาที่กำหนด ระบบควรมีวิธีจัดการรายการที่หมดอายุ เช่น ยกเลิกการจองและคืนจำนวนอุปกรณ์

การดำเนินการนี้ต้องเป็นไปตามเวลาที่กำหนดไว้จริง และไม่ควรยกเลิกรายการที่เจ้าหน้าที่ส่งมอบอุปกรณ์ไปแล้ว

### FR-15 การแสดงสถานะการจอง

ระบบต้องแสดงสถานะของแต่ละรายการให้เข้าใจง่าย เช่น รอรับอุปกรณ์ กำลังยืม คืนแล้ว หรือยกเลิก เพื่อให้ผู้ใช้ทราบว่ารายการของตนอยู่ในขั้นตอนไหน

สถานะที่แสดงต้องตรงกับข้อมูลที่บันทึกไว้ และเปลี่ยนแปลงตามการดำเนินงานจริง

## 3.4 การส่งมอบอุปกรณ์

หลังจากนักศึกษาจองอุปกรณ์แล้ว จะต้องมีขั้นตอนตรวจสอบและส่งมอบโดยเจ้าหน้าที่ เพื่อให้มั่นใจว่ารายการจองถูกต้องและอุปกรณ์ถูกส่งให้ผู้ยืมจริง

### FR-16 การค้นหารายการจอง

เจ้าหน้าที่ต้องสามารถค้นหารายการจองได้จากรหัสอ้างอิงหรือข้อมูลที่ระบบรองรับ เพื่อให้ตรวจสอบรายการได้สะดวกก่อนส่งมอบอุปกรณ์

### FR-17 การใช้ QR Code ค้นหารายการจอง

หากระบบมีฟังก์ชัน QR Code เจ้าหน้าที่ควรสามารถสแกนรหัสเพื่อเปิดดูรายการจองที่เกี่ยวข้องได้

หาก QR Code ไม่ถูกต้องหรือไม่พบรายการ ระบบควรแจ้งข้อผิดพลาดและไม่ดำเนินการเปลี่ยนสถานะของรายการ

### FR-18 การยืนยันส่งมอบอุปกรณ์

เมื่อเจ้าหน้าที่ตรวจสอบข้อมูลและส่งมอบอุปกรณ์ให้ผู้ยืมแล้ว เจ้าหน้าที่จึงสามารถยืนยันการส่งมอบผ่านระบบได้

เมื่อยืนยันสำเร็จ ระบบต้องปรับสถานะรายการและข้อมูลอุปกรณ์ให้ถูกต้อง การสแกน QR Code เพียงอย่างเดียวไม่ถือว่าอุปกรณ์ถูกส่งมอบแล้ว

## 3.5 การรับคืนอุปกรณ์

การรับคืนไม่ได้มีเพียงการนำอุปกรณ์กลับมาเท่านั้น แต่ยังต้องตรวจสอบสภาพและบันทึกข้อมูลให้ครบถ้วน เพื่อให้เจ้าหน้าที่ทราบว่าอุปกรณ์พร้อมให้ยืมต่อหรือจำเป็นต้องซ่อมแซม

### FR-19 การบันทึกการรับคืน

เมื่อผู้ยืมนำอุปกรณ์มาคืน เจ้าหน้าที่ต้องสามารถบันทึกการรับคืนได้ โดยระบบควรเก็บวันและเวลาที่คืนจริง เพื่อใช้ตรวจสอบประวัติและเปรียบเทียบกับกำหนดคืน

### FR-20 การตรวจสอบสภาพอุปกรณ์หลังคืน

ระบบควรให้เจ้าหน้าที่บันทึกสภาพอุปกรณ์หลังรับคืน เช่น สภาพปกติ มีรอยเสียหาย หรือไม่สามารถใช้งานได้ เพื่อให้มีข้อมูลประกอบการตัดสินใจว่าจะนำอุปกรณ์กลับมาให้ยืมได้ทันทีหรือไม่

### FR-21 การปรับสถานะอุปกรณ์หลังรับคืน

เมื่อบันทึกการรับคืนสำเร็จ ระบบต้องปรับข้อมูลการยืมและสถานะอุปกรณ์ให้ถูกต้อง

หากอุปกรณ์อยู่ในสภาพปกติ ก็สามารถกลับไปเป็นอุปกรณ์พร้อมให้ยืมได้ตามเงื่อนไข แต่หากอุปกรณ์ชำรุด ระบบต้องไม่เปลี่ยนสถานะให้พร้อมใช้งานโดยอัตโนมัติ

### FR-22 การตรวจสอบการคืนล่าช้า

ระบบต้องสามารถเปรียบเทียบวันที่คืนจริงกับวันที่กำหนดคืน เพื่อระบุว่ารายการใดคืนตรงเวลาและรายการใดคืนล่าช้า

ข้อมูลนี้ช่วยให้เจ้าหน้าที่ติดตามการยืมได้ง่ายขึ้น และนำไปใช้ดำเนินการตามกฎของโครงการได้

### FR-23 การจัดการอุปกรณ์ชำรุด

หากเจ้าหน้าที่พบว่าอุปกรณ์เสียหายหรือไม่พร้อมใช้งาน ระบบควรรองรับการบันทึกสถานะดังกล่าว เพื่อป้องกันไม่ให้อุปกรณ์ถูกนำไปจองหรือยืมต่อก่อนผ่านการตรวจสอบหรือซ่อมแซม

### FR-24 การป้องกันการบันทึกคืนซ้ำ

เมื่อรายการใดได้รับการยืนยันว่าคืนแล้ว ระบบต้องป้องกันไม่ให้มีการบันทึกการคืนรายการเดิมซ้ำจนทำให้จำนวนอุปกรณ์หรือประวัติการยืมผิดพลาด

## 3.6 การแจ้งเตือน

การแจ้งเตือนช่วยให้ผู้ใช้ไม่พลาดข้อมูลสำคัญ เช่น ผลการจองหรือวันกำหนดคืน อย่างไรก็ตาม ช่องทางและรูปแบบการแจ้งเตือนต้องตรงกับความสามารถที่โครงการพัฒนาจริง

### FR-25 การแจ้งผลการจอง

หากระบบรองรับการแจ้งเตือน ระบบควรแจ้งให้ผู้ใช้ทราบเมื่อจองอุปกรณ์สำเร็จหรือเมื่อเกิดปัญหาที่ทำให้จองไม่สำเร็จ โดยอาจใช้ข้อความบนหน้าจอหรืออีเมลตามที่โครงการกำหนด

### FR-26 การแจ้งเตือนก่อนถึงกำหนดคืน

ระบบควรแจ้งเตือนผู้ใช้ก่อนถึงวันกำหนดคืน เพื่อช่วยให้ผู้ยืมวางแผนและนำอุปกรณ์มาคืนได้ตรงเวลา หากโครงการมีการเปิดใช้ฟังก์ชันนี้

### FR-27 การแจ้งเตือนเมื่อคืนล่าช้า

เมื่อพบว่ารายการยืมเลยกำหนดคืน ระบบควรแจ้งเตือนผู้เกี่ยวข้องตามช่องทางที่กำหนด เพื่อช่วยให้เจ้าหน้าที่ติดตามอุปกรณ์ได้สะดวกขึ้น

### FR-28 การจัดการเมื่อส่งอีเมลไม่สำเร็จ

หากระบบส่งอีเมลไม่สำเร็จ ระบบต้องจัดการข้อผิดพลาดอย่างเหมาะสม และไม่แสดงข้อความว่าการส่งอีเมลสำเร็จหากบริการยังไม่ยืนยันผล

## 3.7 ประวัติการยืมและแดชบอร์ด

ข้อมูลย้อนหลังช่วยให้นักศึกษาตรวจสอบรายการของตนเองได้ ส่วนเจ้าหน้าที่สามารถใช้ข้อมูลภาพรวมเพื่อวางแผนและติดตามการใช้งานอุปกรณ์ได้ง่ายขึ้น

### FR-29 การดูประวัติการยืมของนักศึกษา

ระบบควรแสดงรายการจองและประวัติการยืมของนักศึกษาแต่ละคน เพื่อให้ตรวจสอบได้ว่าเคยยืมอุปกรณ์อะไร ยืมเมื่อใด และคืนแล้วหรือยัง

นักศึกษาแต่ละคนต้องเห็นเฉพาะข้อมูลที่ตนมีสิทธิ์เข้าถึง เพื่อป้องกันการเปิดเผยข้อมูลของผู้อื่น

### FR-30 แดชบอร์ดสำหรับเจ้าหน้าที่

หากระบบมีหน้าแดชบอร์ด ควรแสดงข้อมูลภาพรวมที่ช่วยให้เจ้าหน้าที่ทำงานได้สะดวกขึ้น เช่น จำนวนอุปกรณ์ทั้งหมด จำนวนอุปกรณ์ที่กำลังถูกยืม รายการที่รอรับอุปกรณ์ และรายการที่เลยกำหนดคืน

ข้อมูลที่แสดงต้องตรงกับข้อมูลจริงในระบบ

### FR-31 การตรวจสอบรายการเกินกำหนด

ระบบควรช่วยให้เจ้าหน้าที่ค้นหาและตรวจสอบรายการที่ยังไม่ได้คืนตามกำหนดได้ เพื่อให้ติดตามผู้ยืมและจัดการรายการค้างได้อย่างเป็นระบบ

# 4. ข้อกำหนดด้านคุณภาพของระบบ (Non-functional Requirements)

นอกจากการทำงานได้ถูกต้องแล้ว ระบบยังต้องใช้งานได้สะดวก มีความปลอดภัย และรักษาความถูกต้องของข้อมูลด้วย ข้อกำหนดในบทนี้จึงเน้นคุณภาพของระบบมากกว่าฟังก์ชันเฉพาะอย่างใดอย่างหนึ่ง

## 4.1 ประสิทธิภาพ (Performance)

- ระบบควรตอบสนองต่อการใช้งานทั่วไปได้รวดเร็วเพียงพอ ไม่ทำให้ผู้ใช้ต้องรอนานโดยไม่จำเป็น
- การจองอุปกรณ์ต้องตรวจสอบจำนวนและบันทึกข้อมูลได้อย่างถูกต้อง แม้มีผู้ใช้หลายคนดำเนินการใกล้เคียงกัน
- ควรกำหนดเป้าหมายด้านเวลาตอบสนองและจำนวนผู้ใช้ที่รองรับ แล้วทดสอบก่อนนำระบบไปใช้งานจริง

## 4.2 ความปลอดภัย (Security)

- ผู้ใช้ต้องเข้าสู่ระบบก่อนเข้าถึงข้อมูลที่จำกัดสิทธิ์
- ระบบต้องแยกสิทธิ์ของนักศึกษาและเจ้าหน้าที่อย่างเหมาะสม
- รหัสผ่านต้องได้รับการจัดเก็บด้วยวิธีที่ปลอดภัย ไม่เก็บเป็นข้อความธรรมดา
- ผู้ใช้ต้องไม่สามารถเข้าถึงข้อมูลส่วนตัวของผู้อื่นโดยไม่มีสิทธิ์
- รหัสผ่านฐานข้อมูล API Key และข้อมูลลับอื่น ๆ ต้องไม่ถูกเผยแพร่ใน Repository
- ระบบควรตรวจสอบข้อมูลที่ผู้ใช้ส่งเข้ามาก่อนนำไปประมวลผลหรือบันทึกลงฐานข้อมูล

## 4.3 ความถูกต้องและความน่าเชื่อถือ (Reliability and Integrity)

ระบบต้องทำงานโดยรักษาความถูกต้องของข้อมูลเป็นสำคัญ เช่น เมื่อมีการจองหรือคืนอุปกรณ์ จำนวนคงเหลือต้องเปลี่ยนแปลงอย่างเหมาะสม

หากเกิดข้อผิดพลาดระหว่างดำเนินการ ระบบควรป้องกันไม่ให้ข้อมูลถูกบันทึกเพียงบางส่วนจนเกิดความขัดแย้ง และควรมีวิธีตรวจสอบย้อนหลังสำหรับรายการสำคัญ

## 4.4 ความง่ายในการใช้งาน (Usability)

- หน้าจอควรจัดวางองค์ประกอบให้เข้าใจง่าย ไม่ทำให้ผู้ใช้ต้องคาดเดาว่าควรกดปุ่มใด
- ปุ่มและข้อความควรใช้ภาษาที่ตรงไปตรงมา
- เมื่อทำรายการสำเร็จหรือเกิดข้อผิดพลาด ระบบควรแจ้งผลให้ผู้ใช้ทราบ
- สถานะอุปกรณ์และรายการจองควรแสดงอย่างชัดเจน
- หน้าจอควรเหมาะสมกับอุปกรณ์ที่โครงการกำหนด เช่น คอมพิวเตอร์หรือโทรศัพท์มือถือ

## 4.5 ความง่ายในการดูแลและพัฒนาต่อ (Maintainability)

โค้ดของระบบควรแบ่งออกเป็นส่วน ๆ ตามหน้าที่ เพื่อให้สมาชิกในทีมอ่านและแก้ไขได้สะดวก หากต้องเพิ่มฟังก์ชันในอนาคตก็ควรทำได้โดยไม่กระทบส่วนอื่นมากเกินไป

นอกจากนี้ ควรมี README อธิบายวิธีติดตั้งและเริ่มต้นใช้งาน รวมถึงเอกสารประกอบที่จำเป็นต่อการดูแลระบบ

## 4.6 ความเข้ากันได้ (Compatibility)

ระบบควรทำงานได้บนเว็บเบราว์เซอร์และอุปกรณ์ที่กำหนดไว้ในโครงการ ก่อนส่งมอบควรทดสอบการแสดงผลและการใช้งานจริง เพื่อให้มั่นใจว่าผู้ใช้สามารถเข้าถึงฟังก์ชันสำคัญได้อย่างเหมาะสม

# 5. กฎการยืม–คืนและสถานะของระบบ (Business Rules and Status)

บทนี้อธิบายกฎที่ระบบควรใช้ในการตัดสินใจ เพื่อให้ทุกคนเข้าใจตรงกันว่ากรณีใดสามารถยืมได้ กรณีใดต้องปฏิเสธการจอง และแต่ละสถานะหมายถึงอะไร

## 5.1 กฎการทำงานของระบบ

1. ผู้ใช้ต้องเข้าสู่ระบบก่อนทำรายการที่ต้องใช้สิทธิ์
2. นักศึกษาจะจองอุปกรณ์ได้เมื่อมีจำนวนเพียงพอและผ่านเงื่อนไขของระบบ
3. ระบบต้องไม่ยืนยันการจองที่ทำให้จำนวนอุปกรณ์เกินกว่าที่มีให้ยืม
4. การส่งมอบและรับคืนต้องได้รับการยืนยันจากเจ้าหน้าที่ที่มีสิทธิ์
5. การสแกน QR Code ใช้ค้นหารายการ ไม่ใช่การยืนยันการส่งมอบหรือรับคืนโดยอัตโนมัติ
6. เมื่อยกเลิกการจอง ระบบต้องปรับจำนวนอุปกรณ์ให้ถูกต้อง
7. การคืนล่าช้าและการพักสิทธิ์ต้องดำเนินการตามกฎที่ได้รับอนุมัติ
8. รายการที่ปิดแล้วต้องไม่ถูกดำเนินการซ้ำจนทำให้ข้อมูลผิดพลาด
9. หากอุปกรณ์ชำรุด ต้องไม่ถือว่าอุปกรณ์นั้นพร้อมให้ยืมทันที
10. ผู้ใช้ต้องไม่สามารถแก้ไขหรือเข้าถึงข้อมูลที่อยู่นอกเหนือสิทธิ์ของตนเอง

## 5.2 สถานะการจอง

สถานะช่วยให้ผู้ใช้และเจ้าหน้าที่ทราบว่ารายการจองดำเนินไปถึงขั้นตอนไหนแล้ว

| สถานะ | ความหมาย |
|---|---|
| รอรับอุปกรณ์ | นักศึกษาจองแล้ว แต่เจ้าหน้าที่ยังไม่ได้ยืนยันการส่งมอบ |
| กำลังยืม | เจ้าหน้าที่ยืนยันการส่งมอบแล้ว และอุปกรณ์อยู่กับผู้ยืม |
| คืนแล้ว | เจ้าหน้าที่บันทึกการรับคืนและปิดรายการแล้ว |
| ยกเลิก | รายการจองถูกยกเลิกตามเงื่อนไขที่กำหนด |

ชื่อสถานะจริงอาจแตกต่างจากตารางนี้ได้ จึงควรตรวจสอบกับโค้ดและฐานข้อมูลก่อนนำไปใช้เป็นชื่อสถานะอย่างเป็นทางการ

## 5.3 สถานะอุปกรณ์

อุปกรณ์แต่ละรายการควรมีสถานะที่ช่วยให้ผู้ใช้ทราบว่าสามารถนำไปยืมได้หรือไม่

| สถานะ | ความหมาย |
|---|---|
| ว่าง | อุปกรณ์พร้อมให้ยืมตามจำนวนที่มีอยู่ |
| ถูกจอง | มีการจองอุปกรณ์ไว้แล้วตามเงื่อนไขของระบบ |
| ถูกยืมอยู่ | อุปกรณ์อยู่ระหว่างการยืม |
| ปิดใช้งานหรือรอซ่อม | อุปกรณ์ไม่พร้อมให้ยืม เช่น ชำรุดหรืออยู่ระหว่างตรวจสอบ |

ในกรณีที่อุปกรณ์มีหลายชิ้น ระบบควรแยกจำนวนทั้งหมด จำนวนที่ถูกจอง จำนวนที่ถูกยืม และจำนวนที่พร้อมให้ยืมให้ชัดเจน เพื่อป้องกันความสับสน

## 5.4 สถานะบัญชีผู้ใช้

| สถานะ | ความหมาย |
|---|---|
| ปกติ | ผู้ใช้สามารถจองอุปกรณ์ได้หากผ่านเงื่อนไขอื่น |
| ถูกพักสิทธิ์ชั่วคราว | ผู้ใช้ไม่สามารถจองใหม่ได้ในช่วงเวลาที่ถูกพักสิทธิ์ |

การพักสิทธิ์ควรใช้เฉพาะเมื่อโครงการกำหนดกฎนี้ไว้ชัดเจนแล้ว และต้องมีวิธีตรวจสอบวันที่เริ่มต้นกับวันที่สิ้นสุดของการพักสิทธิ์

## 5.5 ค่าที่ต้องตกลงให้ชัดเจน

ก่อนนำระบบไปใช้งานจริง ทีมควรตกลงรายละเอียดต่อไปนี้ให้ตรงกัน

- นักศึกษาสามารถยืมอุปกรณ์ได้นานที่สุดกี่วัน
- หลังจองแล้วต้องมารับอุปกรณ์ภายในกี่ชั่วโมง
- ระบบจะยกเลิกการจองที่หมดอายุเมื่อใด
- จะถือว่าคืนล่าช้าเมื่อเลยเวลาใด
- หากคืนล่าช้า จะมีการพักสิทธิ์หรือไม่ และเป็นระยะเวลาเท่าใด
- ระบบจะแจ้งเตือนก่อนคืนเมื่อใด
- จะใช้ช่องทางใดในการแจ้งเตือนผู้ใช้

ค่าต่าง ๆ เหล่านี้ไม่ควรกำหนดขึ้นเองโดยไม่มีการตกลงจากผู้รับผิดชอบโครงการหรืออาจารย์

# 6. ข้อกำหนดด้านข้อมูล (Data Requirements)

ข้อมูลเป็นส่วนสำคัญของระบบ เพราะทุกขั้นตอนตั้งแต่การจองไปจนถึงการคืนอุปกรณ์ต้องอาศัยข้อมูลที่ถูกต้อง หากข้อมูลไม่ตรงกัน อาจทำให้ผู้ใช้จองอุปกรณ์ไม่ได้หรือทำให้เจ้าหน้าที่ติดตามรายการผิดพลาดได้

## 6.1 ข้อมูลที่ระบบควรจัดเก็บ

| กลุ่มข้อมูล | รายละเอียด |
|---|---|
| ข้อมูลผู้ใช้ | รหัสผู้ใช้ อีเมล บทบาท และสถานะบัญชีตามความจำเป็น |
| ข้อมูลอุปกรณ์ | รหัสอุปกรณ์ ชื่อ ประเภท จำนวนทั้งหมด จำนวนพร้อมให้ยืม และสถานะ |
| ข้อมูลการจอง | รหัสการจอง ผู้จอง อุปกรณ์ วันที่เริ่มยืม วันกำหนดคืน เวลาหมดอายุ และสถานะ |
| ข้อมูลการส่งมอบ | วันและเวลาที่ส่งมอบ ผู้ดำเนินการ และผลการตรวจสอบสภาพก่อนส่งมอบ หากมี |
| ข้อมูลการรับคืน | วันและเวลาที่คืนจริง ผู้ดำเนินการ และผลการตรวจสอบสภาพหลังคืน หากมี |
| ข้อมูลการแจ้งเตือน | ผู้รับ ประเภทการแจ้งเตือน เวลา และผลการส่ง หากระบบจัดเก็บ |
| ข้อมูลการพักสิทธิ์ | ผู้ใช้ เหตุผล ระยะเวลาพักสิทธิ์ และผู้ดำเนินการ หากระบบรองรับ |

ตารางนี้เป็นเพียงภาพรวมของข้อมูลที่ระบบอาจจำเป็นต้องใช้ ไม่ใช่การยืนยันว่าฐานข้อมูลจริงมีตารางและฟิลด์เหล่านี้ทั้งหมด ต้องตรวจสอบกับโครงสร้างฐานข้อมูลของโครงการก่อนจัดทำ Data Dictionary และ ER Diagram

## 6.2 การรักษาความถูกต้องของข้อมูล

ระบบควรดูแลให้ข้อมูลมีความถูกต้องและเชื่อมโยงกันได้ โดยมีแนวทางดังนี้

1. รหัสของรายการแต่ละรายการต้องไม่ซ้ำกัน
2. การจองต้องอ้างอิงผู้ใช้และอุปกรณ์ที่มีอยู่จริง
3. วันที่เริ่มยืมต้องไม่ขัดกับวันที่กำหนดคืน
4. จำนวนอุปกรณ์พร้อมให้ยืมต้องไม่ติดลบ
5. การยกเลิกและการรับคืนต้องไม่ทำให้จำนวนอุปกรณ์เพิ่มขึ้นซ้ำโดยไม่ถูกต้อง
6. ผู้ใช้ต้องเข้าถึงข้อมูลได้ตามสิทธิ์ของตนเอง
7. หากเกิดข้อผิดพลาดในการบันทึก ระบบต้องจัดการไม่ให้ข้อมูลบางส่วนค้างอยู่ในสถานะที่ไม่ถูกต้อง

# 7. ส่วนติดต่อผู้ใช้และการเชื่อมต่อกับระบบอื่น (Interfaces)

บทนี้อธิบายว่าผู้ใช้จะติดต่อกับระบบผ่านหน้าจอใดบ้าง และระบบต้องเชื่อมต่อกับส่วนอื่นอย่างไร เพื่อให้การทำงานตั้งแต่การจองจนถึงการรับคืนดำเนินไปได้อย่างถูกต้อง

## 7.1 หน้าจอสำหรับผู้ใช้งาน (User Interface)

ระบบควรมีหน้าจอให้เหมาะกับหน้าที่ของนักศึกษาและเจ้าหน้าที่ โดยหน้าจอที่อาจจำเป็น ได้แก่

- หน้าเข้าสู่ระบบ เพื่อให้ผู้ใช้ยืนยันตัวตน
- หน้ารายการอุปกรณ์ เพื่อให้ดูรายละเอียดและจำนวนที่พร้อมให้ยืม
- หน้าจองอุปกรณ์ เพื่อเลือกอุปกรณ์และกำหนดวันยืม–คืน
- หน้ารายละเอียดการจอง เพื่อดูสถานะและข้อมูลที่เกี่ยวข้อง
- หน้าประวัติการยืม เพื่อให้นักศึกษาตรวจสอบรายการของตนเอง
- หน้าค้นหารายการจองสำหรับเจ้าหน้าที่
- หน้ายืนยันส่งมอบและรับคืนอุปกรณ์
- หน้าจัดการข้อมูลอุปกรณ์สำหรับเจ้าหน้าที่
- หน้าแดชบอร์ดสำหรับดูภาพรวม หากมีในระบบจริง
- หน้าหรือส่วนแสดงการแจ้งเตือนและสถานะพักสิทธิ์ หากระบบรองรับ

รายการเหล่านี้เป็นแนวทางในการกำหนดหน้าจอ ไม่ใช่การยืนยันว่าทุกหน้ามีอยู่ในระบบปัจจุบัน

## 7.2 การเชื่อมต่อฐานข้อมูล

ระบบต้องสามารถอ่านและบันทึกข้อมูลที่จำเป็นได้ เช่น ข้อมูลอุปกรณ์ ข้อมูลผู้ใช้ และรายการจอง

หากไม่สามารถเชื่อมต่อฐานข้อมูลหรือบันทึกข้อมูลได้ ระบบควรแจ้งข้อผิดพลาดอย่างเหมาะสม และไม่แสดงผลว่าทำรายการสำเร็จทั้งที่ข้อมูลยังไม่ได้รับการบันทึกอย่างถูกต้อง

รายละเอียดเกี่ยวกับชนิดฐานข้อมูลและโครงสร้างตารางต้องอ้างอิงจากไฟล์ของโครงการจริง

## 7.3 การเชื่อมต่อบริการอีเมล

หากระบบใช้การแจ้งเตือนผ่านอีเมล ต้องตั้งค่าบริการให้ถูกต้องและตรวจสอบผลการส่งอย่างเหมาะสม

ข้อมูลสำคัญ เช่น รหัสผ่านของบริการหรือคีย์ที่ใช้เชื่อมต่อ ต้องจัดเก็บอย่างปลอดภัย ไม่ควรเขียนข้อมูลลับลงในโค้ดหรือเผยแพร่ไว้ใน Repository

## 7.4 การใช้ QR Code

QR Code ช่วยให้เจ้าหน้าที่ค้นหารายการจองได้รวดเร็วขึ้น โดยรหัสต้องเชื่อมโยงกับรายการที่ถูกต้อง

อย่างไรก็ตาม การสแกน QR Code เป็นเพียงขั้นตอนค้นหาข้อมูล เจ้าหน้าที่ยังคงต้องตรวจสอบรายการและยืนยันการส่งมอบหรือรับคืนตามขั้นตอนของระบบ

# 8. เกณฑ์การยอมรับระบบ (Acceptance Criteria)

เมื่อพัฒนาระบบเสร็จแล้ว ทีมควรทดสอบว่าระบบทำงานได้ตามข้อกำหนดหรือไม่ โดยพิจารณาจากสถานการณ์ที่อาจเกิดขึ้นจริงในการใช้งาน

ตารางต่อไปนี้เป็นตัวอย่างเกณฑ์การทดสอบที่สามารถนำไปปรับให้ตรงกับฟังก์ชันของระบบได้

| รหัส | สถานการณ์ที่ทดสอบ | ผลลัพธ์ที่คาดหวัง |
|---|---|---|
| AC-01 | ผู้ใช้เข้าสู่ระบบด้วยข้อมูลถูกต้อง | เข้าสู่ระบบได้และเห็นฟังก์ชันตามสิทธิ์ |
| AC-02 | ผู้ใช้กรอกอีเมลหรือรหัสผ่านไม่ถูกต้อง | ระบบปฏิเสธการเข้าสู่ระบบและแจ้งข้อผิดพลาด |
| AC-03 | นักศึกษาจองอุปกรณ์ที่มีจำนวนพร้อมให้ยืม | ระบบสร้างรายการจองและบันทึกข้อมูลถูกต้อง |
| AC-04 | นักศึกษาจองอุปกรณ์ที่ไม่มีจำนวนพร้อมให้ยืม | ระบบไม่สร้างรายการจองเกินจำนวน |
| AC-05 | ผู้ใช้ที่ถูกพักสิทธิ์พยายามจองอุปกรณ์ | ระบบปฏิเสธการจองตามกฎที่กำหนด |
| AC-06 | นักศึกษายกเลิกรายการจองที่ยังไม่ส่งมอบ | ระบบยกเลิกรายการและปรับจำนวนอุปกรณ์ถูกต้อง |
| AC-07 | เจ้าหน้าที่สแกน QR Code ของรายการที่รอรับ | ระบบแสดงข้อมูลรายการโดยยังไม่ยืนยันการส่งมอบ |
| AC-08 | เจ้าหน้าที่ยืนยันส่งมอบอุปกรณ์ | ระบบปรับสถานะการจองและข้อมูลอุปกรณ์ถูกต้อง |
| AC-09 | เจ้าหน้าที่บันทึกการรับคืนอุปกรณ์ | ระบบบันทึกเวลาคืนและปรับสถานะได้ถูกต้อง |
| AC-10 | นักศึกษาคืนอุปกรณ์หลังวันกำหนดคืน | ระบบระบุรายการคืนล่าช้าได้ตามกฎ |
| AC-11 | รายการจองหมดอายุและผู้จองไม่มารับอุปกรณ์ | ระบบจัดการรายการตามกฎหมดอายุที่กำหนด |
| AC-12 | ผู้ใช้พยายามเปิดหน้าที่ตนไม่มีสิทธิ์เข้าถึง | ระบบปฏิเสธการเข้าถึง |
| AC-13 | ระบบส่งอีเมลแจ้งเตือนไม่สำเร็จ | ระบบจัดการข้อผิดพลาดโดยไม่รายงานว่าส่งสำเร็จ |

การทดสอบควรบันทึกข้อมูลที่ใช้ทดสอบ ขั้นตอนการทดสอบ ผลลัพธ์ที่คาดหวัง และผลลัพธ์ที่เกิดขึ้นจริง เพื่อให้ทีมทราบว่าข้อกำหนดใดผ่านการทดสอบแล้วและข้อใดยังต้องแก้ไข

**ข้อสำคัญ:** เกณฑ์ในตารางเป็นผลลัพธ์ที่คาดหวัง ไม่ใช่ผลการทดสอบจริง จึงไม่ควรระบุว่าระบบผ่านการทดสอบจนกว่าจะได้ทดลองใช้งานและบันทึกผลแล้ว

# 9. รายการที่ต้องตรวจสอบก่อนอนุมัติเอกสาร

แม้เอกสารฉบับนี้จะอธิบายภาพรวมของระบบไว้แล้ว แต่ยังมีรายละเอียดบางอย่างที่ต้องตรวจสอบกับโครงการจริง เพื่อให้เอกสารตรงกับสิ่งที่ทีมพัฒนาขึ้น

รายการที่ควรตรวจสอบมีดังนี้

- [ ] ตรวจสอบโครงสร้างและฟังก์ชันของ Frontend
- [ ] ตรวจสอบโครงสร้างและการทำงานของ Backend
- [ ] ตรวจสอบชนิดฐานข้อมูลและโครงสร้างตารางจริง
- [ ] ตรวจสอบวิธีเข้าสู่ระบบและการแบ่งสิทธิ์
- [ ] ตรวจสอบว่าระบบสร้างและสแกน QR Code ได้จริงหรือไม่
- [ ] ตรวจสอบวิธีคำนวณจำนวนอุปกรณ์ที่พร้อมให้ยืม
- [ ] ตรวจสอบการป้องกันกรณีผู้ใช้หลายคนจองพร้อมกัน
- [ ] ตรวจสอบว่ามีงานอัตโนมัติสำหรับจัดการรายการหมดอายุหรือไม่
- [ ] ยืนยันกฎการคืนล่าช้าและการพักสิทธิ์
- [ ] ตรวจสอบว่าระบบส่งอีเมลแจ้งเตือนได้จริงหรือไม่
- [ ] กำหนดเป้าหมายด้านประสิทธิภาพและวิธีทดสอบ
- [ ] ตรวจสอบข้อกำหนดเพิ่มเติมจากอาจารย์
- [ ] ทดสอบฟังก์ชันสำคัญและบันทึกผลการทดสอบจริง

เมื่อดำเนินการครบแล้ว ทีมจึงควรปรับสถานะเอกสารจากร่างเป็นฉบับที่ผ่านการทบทวน

# 10. การเชื่อมโยงข้อกำหนดกับการทดสอบ (Requirements Traceability)

การกำหนดรหัสให้ข้อกำหนดแต่ละข้อช่วยให้ทีมติดตามงานได้ง่ายขึ้น เช่น เมื่อมีการแก้ไขฟังก์ชันการจอง ทีมจะสามารถตรวจสอบได้ว่าต้องทดสอบส่วนใดบ้าง

ตารางต่อไปนี้แสดงตัวอย่างการเชื่อมโยงระหว่างข้อกำหนด ฟังก์ชัน และการทดสอบ

| ข้อกำหนด | ฟังก์ชันที่เกี่ยวข้อง | สิ่งที่ควรทดสอบ |
|---|---|---|
| FR-01 ถึง FR-04 | การเข้าสู่ระบบและการจัดการสิทธิ์ | เข้าสู่ระบบด้วยข้อมูลถูกต้อง ข้อมูลผิด และการเข้าถึงโดยไม่มีสิทธิ์ |
| FR-05 ถึง FR-08 | การดูและจัดการอุปกรณ์ | การแสดงรายการ การแก้ไขข้อมูล และการปรับจำนวน |
| FR-09 ถึง FR-15 | การจองและยกเลิกการจอง | จำนวนอุปกรณ์ไม่พอ การจองพร้อมกัน การยกเลิก และรายการหมดอายุ |
| FR-16 ถึง FR-18 | การค้นหารายการและส่งมอบอุปกรณ์ | การค้นหารายการ การสแกน QR Code และการยืนยันส่งมอบ |
| FR-19 ถึง FR-24 | การรับคืนและการจัดการอุปกรณ์ | การคืนตรงเวลา การคืนล่าช้า อุปกรณ์ชำรุด และการป้องกันการคืนซ้ำ |
| FR-25 ถึง FR-28 | การแจ้งเตือน | การส่งแจ้งเตือนและการจัดการเมื่อส่งไม่สำเร็จ |
| FR-29 ถึง FR-31 | ประวัติการยืมและแดชบอร์ด | ความถูกต้องของข้อมูลและการจำกัดสิทธิ์การเข้าถึง |

การเชื่อมโยงนี้จะช่วยให้ทีมตรวจสอบได้ว่าแต่ละข้อกำหนดมีวิธีทดสอบรองรับหรือไม่ และลดโอกาสที่ฟังก์ชันสำคัญจะถูกมองข้าม

# ภาคผนวก A: รายการค่าที่ต้องยืนยัน

ก่อนนำระบบไปใช้งานจริง ควรกำหนดรายละเอียดต่อไปนี้ให้ชัดเจน เพื่อให้ทั้งทีมพัฒนาและผู้ใช้งานเข้าใจกฎตรงกัน

| รายการ | ข้อมูลเบื้องต้น | สิ่งที่ต้องดำเนินการ |
|---|---|---|
| ระยะเวลายืมสูงสุด | มีตัวอย่างในเอกสารโครงการเดิมว่าไม่เกิน 7 วัน | ตรวจสอบและยืนยันกฎจริง |
| เวลาที่ต้องมารับอุปกรณ์ | มีตัวอย่างว่า 24 ชั่วโมงหลังจอง | ตรวจสอบเงื่อนไขจริง |
| การจัดการรายการจองหมดอายุ | ต้องกำหนดวิธีและเวลาที่ระบบตรวจสอบ | ตรวจสอบโค้ดและยืนยันกฎ |
| การคืนล่าช้า | ยังต้องยืนยันเกณฑ์ที่ใช้ตัดสิน | ตกลงกับผู้รับผิดชอบระบบ |

# ภาคผนวก B: แนวทางจัดเก็บเอกสารใน Repository

เพื่อให้สมาชิกในทีมค้นหาเอกสารได้สะดวก ควรจัดเก็บไฟล์ SRS ไว้ในโฟลเดอร์ `docs/` โดยใช้ชื่อไฟล์ `SRS.md`

ตัวอย่างโครงสร้างไฟล์ที่แนะนำคือ

```text
it-device-borrowing-system/
├── README.md
├── docs/
│   ├── SRS.md
│   ├── UseCase.md
│   ├── DataDictionary.md
│   └── TestCases.md
└── ...
```

โครงสร้างนี้เป็นเพียงตัวอย่าง สามารถปรับให้เข้ากับโครงสร้าง Repository ที่มีอยู่จริงได้

เมื่อจัดทำเอกสารส่วนอื่นเพิ่มเติมแล้ว ควรเพิ่มลิงก์ไปยังเอกสารเหล่านั้นใน README เพื่อให้สมาชิกในทีมและอาจารย์เข้าถึงข้อมูลได้ง่ายขึ้น

## สรุป

ระบบยืม–คืนอุปกรณ์ไอทีมีเป้าหมายเพื่อช่วยให้การจัดการอุปกรณ์ภายในสถานศึกษาสะดวกและเป็นระบบมากขึ้น นักศึกษาสามารถตรวจสอบและจองอุปกรณ์ได้ ส่วนเจ้าหน้าที่สามารถดูแลข้อมูล ตรวจสอบรายการจอง และบันทึกการส่งมอบกับรับคืนได้อย่างถูกต้อง
