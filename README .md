# ระบบยืม–คืนอุปกรณ์ไอที (IT Equipment Borrowing System)

ระบบจัดการยืม-คืนอุปกรณ์ไอทีผ่านเว็บ สำหรับสถาบันการศึกษาระดับอาชีวศึกษา ให้นักศึกษาจองอุปกรณ์ล่วงหน้า รับ-คืนผ่านการยืนยันของเจ้าหน้าที่ พร้อมระบบแจ้งเตือนอัตโนมัติและบทลงโทษกรณีคืนเกินกำหนด

---

## 1. ภาพรวมปัญหาที่ระบบแก้ไข

สถาบันที่ไม่มีระบบดิจิทัล นักศึกษาต้องเดินไปโดยไม่รู้ล่วงหน้าว่าอุปกรณ์ที่ต้องการยืมว่างอยู่หรือไม่ อาจไปถึงแล้วพบว่ามีคนยืมไปก่อน ระบบนี้แก้ปัญหาด้วยการแสดงจำนวนอุปกรณ์คงเหลือแบบเรียลไทม์ และบังคับให้จองผ่านระบบก่อนเท่านั้นจึงจะยืมได้ เพื่อความเป็นธรรมและโปร่งใสต่อผู้ใช้ทุกคน

---

## 2. ผู้ใช้งานระบบ (User Roles)

| บทบาท | สิทธิ์การใช้งาน |
|---|---|
| **นักศึกษา (Student)** | ดูรายการอุปกรณ์, จอง/ยกเลิกการจอง, ดูประวัติการยืมของตนเอง, รับอีเมลแจ้งเตือน |
| **เจ้าหน้าที่ (Staff)** | จัดการคลังอุปกรณ์, ยืนยันส่งมอบ/รับคืน, ดูแดชบอร์ดภาพรวม, ดูรายชื่อผู้ใช้ที่ถูกพักสิทธิ์ |

---

## 3. นิยามสถานะหลักของระบบ (Core Statuses)

ระบบทั้งหมดขับเคลื่อนด้วย 3 สถานะหลักเท่านั้น ทุกฟังก์ชันคือกลไกที่ทำให้ 3 สถานะนี้เปลี่ยนแปลงอย่างถูกต้อง:

### 3.1 สถานะอุปกรณ์ (นับเป็นจำนวนคงเหลือ ไม่ใช่ true/false)
- แสดงผลแบบ `เหลือ X / ทั้งหมด Y` เช่น "โน้ตบุ๊ก เหลือ 2/5"
- เมื่อจำนวนคงเหลือ = 0 → ปุ่มจองถูกปิดอัตโนมัติ แสดง "ของหมด"
- อุปกรณ์แต่ละชิ้นมีสถานะย่อย: `ว่าง` → `ถูกจอง` → `ถูกยืมอยู่` → กลับเป็น `ว่าง` | หรือ `ปิดใช้งาน` (ชำรุด/ส่งซ่อม)

### 3.2 สถานะการจอง (Booking Status)
`รอรับของ` → `กำลังยืม` → `คืนแล้ว` (ปิดเคส)
หรือแตกเป็น: `เกินกำหนด` (ระหว่างกำลังยืมแต่เลยวันคืน) / `ยกเลิก` (โดยนักศึกษาเองหรือระบบอัตโนมัติกรณีไม่มารับ)

### 3.3 สถานะบัญชีผู้ใช้ (User Account Status)
`ปกติ` (จองได้) ↔ `ถูกพักสิทธิ์ชั่วคราว` (ห้ามจองของใหม่เท่านั้น — ไม่กระทบสิทธิ์อื่น เช่น login หรือดูประวัติยังทำได้ปกติ) → กลับเป็น `ปกติ` อัตโนมัติเมื่อครบกำหนดพัก

---

## 4. Flow การทำงานฉบับสมบูรณ์ (ตั้งแต่ต้นจนจบ)

### ขั้นตอนที่ 1 — การจอง (Booking)
1. นักศึกษา login เข้าระบบด้วยอีเมล + รหัสผ่าน
2. ระบบตรวจสอบสถานะบัญชี:
   - ถ้า `ถูกพักสิทธิ์` → แสดงข้อความเตือน + วันที่จะกลับมาจองได้ → หยุด ไม่ให้จองต่อ
   - ถ้า `ปกติ` → ไปขั้นตอนถัดไป
3. นักศึกษาเลือกอุปกรณ์ที่ยังมีจำนวนคงเหลือ > 0
4. เลือกวันที่เริ่มยืม–วันที่คืน (ระบบจำกัดจำนวนวันสูงสุดต่อครั้ง เช่น ไม่เกิน 7 วัน)
5. กด "ยืนยันการจอง" → ระบบตรวจสอบอีกครั้งว่าของยังเหลือจริงในช่วงเวลานั้น (กันการจองซ้อนกรณีมีคนกดพร้อมกัน)
6. เมื่อผ่านการตรวจสอบ ระบบทำพร้อมกัน 3 อย่าง:
   - ลดจำนวนอุปกรณ์คงเหลือลง 1 ทันที (เปลี่ยนสถานะอุปกรณ์ชิ้นนั้นเป็น `ถูกจอง`)
   - สร้าง Booking ID พร้อม QR Code ผูกกับการจองนี้
   - ตั้งเวลาหมดอายุการจอง (เช่น ต้องมารับภายใน 24 ชั่วโมง)
7. ส่งอีเมลยืนยันการจอง แนบ QR Code พร้อมแจ้งเงื่อนไขเวลาที่ต้องมารับ

**เส้นทางย่อยที่ต้องมี:**
- **นักศึกษายกเลิกเอง**: ทำได้ตราบใดที่สถานะยังเป็น `รอรับของ` → กดยกเลิกจากหน้า "การจองของฉัน" → จำนวนอุปกรณ์คงเหลือบวกกลับทันที
- **ไม่มารับตามเวลา (No-show)**: เมื่อเลยเวลาหมดอายุการจองแล้วยังไม่มารับ → ระบบอัตโนมัติ (ทำงานเป็นรอบ เช่น ทุก 1 ชั่วโมง) ยกเลิก Booking ให้เอง → จำนวนอุปกรณ์คงเหลือบวกกลับทันที → ส่งอีเมลแจ้งว่าการจองถูกยกเลิก

### ขั้นตอนที่ 2 — การรับอุปกรณ์ (Pickup)
8. นักศึกษามาที่เคาน์เตอร์ เปิด QR Code จากอีเมล/หน้า "การจองของฉัน"
9. เจ้าหน้าที่สแกน QR Code → ระบบดึงข้อมูลการจองขึ้นแสดงบนหน้าจอเจ้าหน้าที่ **(ขั้นตอนนี้เป็นเพียงการค้นหาข้อมูล ยังไม่ใช่การยืนยัน)**
10. ระบบตรวจสอบว่าสถานะการจองยังเป็น `รอรับของ` อยู่หรือไม่ — ถ้าถูกยกเลิก/หมดอายุไปแล้ว แจ้งเตือนเจ้าหน้าที่ทันที
11. เจ้าหน้าที่ตรวจสอบตัวตนผู้มารับ และสภาพอุปกรณ์ก่อนส่งมอบ บันทึกผล (ปกติ/มีตำหนิระบุรายละเอียด)
12. เจ้าหน้าที่กดปุ่ม **"ยืนยันส่งมอบอุปกรณ์"** (จุดยืนยันจริงโดยมนุษย์เสมอ ไม่ใช่การสแกนอัตโนมัติ)
13. ระบบเปลี่ยนสถานะ:
    - Booking: `รอรับของ` → `กำลังยืม` (เริ่มนับวันคืนจริง ณ ตอนนี้)
    - อุปกรณ์: `ถูกจอง` → `ถูกยืมอยู่`

### ขั้นตอนที่ 3 — ระหว่างการยืม (แจ้งเตือน)
14. ระบบตรวจสอบเป็นรอบ (วันละ 1 ครั้ง ไม่ต้อง real-time):
    - เหลือ 1 วันก่อนครบกำหนด → ส่งอีเมลแจ้งเตือน 1 ครั้ง
    - ถึงวันครบกำหนดพอดี → ส่งอีเมลแจ้งเตือน 1 ครั้ง
    - เลยวันครบกำหนดไปแล้วยังไม่คืน → เปลี่ยนสถานะ Booking เป็น `เกินกำหนด` + ส่งอีเมลแจ้งเตือนซ้ำวันละครั้งจนกว่าจะคืน

### ขั้นตอนที่ 4 — การคืนอุปกรณ์ (Return)
15. นักศึกษานำอุปกรณ์มาคืนที่เคาน์เตอร์
16. เจ้าหน้าที่ค้นหา/สแกน Booking (ผ่าน QR เดิม หรือค้นชื่อ/รหัสนักศึกษา)
17. เจ้าหน้าที่ตรวจสภาพอุปกรณ์ตอนคืน บันทึกผล — ถ้าชำรุด เจ้าหน้าที่สามารถเปลี่ยนสถานะอุปกรณ์ชิ้นนั้นเป็น `ปิดใช้งาน` แยกไปรอซ่อมได้ทันที (ไม่ต้องรอรอบซ่อมประจำปี)
18. เจ้าหน้าที่กดปุ่ม **"ยืนยันรับคืน"**
19. ระบบตรวจสอบอัตโนมัติ: วันที่คืนจริง เทียบกับวันครบกำหนด
    - **คืนตรงเวลา** → ปิดเคส Booking เป็น `คืนแล้ว` → จำนวนอุปกรณ์คงเหลือบวกกลับทันที
    - **คืนเกินกำหนด** → คำนวณจำนวนวันที่เกิน → ถ้าเกิน ≥ เกณฑ์ที่ตั้งไว้ (เช่น 1 วันขึ้นไป) → ตั้งสถานะบัญชีผู้ใช้เป็น `ถูกพักสิทธิ์` อัตโนมัติ 1-2 วัน (นับจากวันคืนจริง) → จำนวนอุปกรณ์คงเหลือบวกกลับทันทีเช่นกัน (อุปกรณ์กลับเข้าคลังตามปกติ มีผลเฉพาะกับสิทธิ์การจองของผู้ยืมเท่านั้น)
20. ส่งอีเมลยืนยันการคืนสำเร็จ พร้อมระบุว่าตรงเวลาหรือมีบทลงโทษหรือไม่
21. เมื่อครบกำหนดระยะเวลาพักสิทธิ์ ระบบเปลี่ยนบัญชีผู้ใช้กลับเป็น `ปกติ` ให้อัตโนมัติ โดยไม่ต้องมีเจ้าหน้าที่ปลดล็อกเอง

## 5. รายการฟังก์ชันทั้งหมด แบ่งตามโมดูล (Functional Requirements)

### โมดูล A: บัญชีผู้ใช้ (Authentication)
- Login / Logout ด้วยอีเมลสถาบัน + รหัสผ่าน
- ลืมรหัสผ่าน (reset ผ่านอีเมล)
- แบ่งสิทธิ์ 2 ระดับ: นักศึกษา และ เจ้าหน้าที่

### โมดูล B: คลังอุปกรณ์ (Inventory Management)
- แสดงรายการอุปกรณ์พร้อมจำนวนคงเหลือแบบเรียลไทม์
- ค้นหา/กรองตามหมวดหมู่
- เจ้าหน้าที่: เพิ่ม/แก้ไข/ปิดใช้งานอุปกรณ์ (กรณีส่งซ่อมหรือชำรุด)

### โมดูล C: การจอง (Booking)
- เลือกวันยืม–วันคืน พร้อมจำกัดจำนวนวันสูงสุดต่อครั้ง
- ตรวจสอบความขัดแย้งของการจอง (ป้องกันจองซ้อนช่วงเวลาเดียวกันเมื่อของไม่พอ)
- ยกเลิกการจองได้เองก่อนถึงขั้นตอนรับของ
- ยกเลิกอัตโนมัติเมื่อไม่มารับตามเวลาที่กำหนด
- สร้าง QR Code ต่อ 1 การจอง

### โมดูล D: การส่งมอบ/รับคืน (Pickup & Return — ฝั่งเจ้าหน้าที่)
- สแกน/ค้นหา QR เพื่อดึงข้อมูลการจอง
- ยืนยันส่งมอบโดยเจ้าหน้าที่ (แยกขั้นตอนจากการสแกน)
- บันทึกสภาพอุปกรณ์ตอนส่งมอบและตอนรับคืน
- ยืนยันรับคืน พร้อมคำนวณความล่าช้าอัตโนมัติ
- ปุ่มแจ้งอุปกรณ์ชำรุดระหว่างการตรวจสอบ

### โมดูล E: ระบบแจ้งเตือน (Notification Engine)
- Trigger: จองสำเร็จ / ใกล้ครบกำหนด / ถึงกำหนด / เกินกำหนด (ซ้ำรายวัน) / ถูกพักสิทธิ์ / คืนสำเร็จ / ยกเลิกอัตโนมัติ
- ช่องทางหลัก: อีเมล

### โมดูล F: ระบบบทลงโทษ (Penalty System)
- กำหนดเกณฑ์วันที่เกินกำหนดและจำนวนวันพักสิทธิ์ได้ (ปรับตั้งค่าได้)
- แสดงสถานะ "ถูกพักสิทธิ์ถึงวันที่..." ในหน้าโปรไฟล์ผู้ใช้
- ปลดสิทธิ์อัตโนมัติเมื่อครบกำหนด หรือเจ้าหน้าที่ปลดล็อกได้เองกรณีพิเศษ

### โมดูล G: ประวัติและแดชบอร์ด (History & Dashboard)
- ฝั่งนักศึกษา: ประวัติการยืมของตนเอง แยกตามสถานะ
- ฝั่งเจ้าหน้าที่: สรุปภาพรวม (จำนวนที่กำลังยืม, เกินกำหนด, ผู้ใช้ถูกพักสิทธิ์)

## 6. ผลการตรวจสอบความครบถ้วนของ Flow (Consistency Check)

| จุดเชื่อมต่อ | สถานะการตรวจสอบ |
|---|---|
| จอง → กันของไม่ให้คนอื่นจองซ้อน | ครบถ้วน |
| จองแล้วไม่มารับ → คืนของอัตโนมัติ | ครบถ้วน |
| จองแล้วเปลี่ยนใจ → ยกเลิกเอง | ครบถ้วน |
| สแกน QR → ต้องมีเจ้าหน้าที่ยืนยันซ้ำเสมอ | ครบถ้วน (ป้องกัน QR หลุด/ส่งต่อ) |
| คืนเกินกำหนด → คำนวณบทลงโทษอัตโนมัติ | ครบถ้วน |
| บทลงโทษ → จำกัดผลแค่ "จองใหม่ไม่ได้" เท่านั้น | ครบถ้วน |
| อุปกรณ์ชำรุด → ตัดออกจากคลังทันทีที่พบ ไม่ต้องรอรอบซ่อมประจำปี | ครบถ้วน |
| ทุกจุดที่อุปกรณ์เปลี่ยนสถานะ (จอง/ยกเลิก/หมดเวลา/รับ/คืน) → จำนวนคงเหลืออัปเดตถูกต้องทุกครั้ง | ครบถ้วน |

**สรุป:** Flow ไม่มีจุดค้าง (dead-end) และไม่มีฟังก์ชันที่ขาดหายจากเส้นทางหลัก เหมาะสำหรับพัฒนาโดยทีมขนาดเล็ก (นักพัฒนา 1 คน) ในระดับสถาบันอาชีวศึกษา

## 7. Prompt สำหรับนำไปพัฒนาโปรเจกต์ (Development Prompt)

> คัดลอกข้อความด้านล่างนี้ทั้งหมด ไปวางใน AI coding assistant (เช่น Claude Code, Cursor, ChatGPT) เพื่อเริ่มพัฒนาระบบตามลำดับขั้นตอน

```
ช่วยพัฒนาเว็บแอปพลิเคชัน "ระบบยืม–คืนอุปกรณ์ไอที" สำหรับสถาบันอาชีวศึกษา ตามข้อกำหนดต่อไปนี้ทีละขั้นตอนตามลำดับ:

บริบท: ผู้พัฒนาเป็นนักศึกษา ทำโปรเจกต์กับทีม 3 คน (เดฟหลักคนเดียว) ต้องการระบบที่ใช้งานได้จริง ไม่ซับซ้อนเกินความจำเป็น

ผู้ใช้งานมี 2 บทบาท: นักศึกษา (Student) และ เจ้าหน้าที่ (Staff)

สถานะหลักของระบบ 3 ชุด:
1. สถานะอุปกรณ์: นับเป็นจำนวนคงเหลือ (เช่น เหลือ 2/5) แต่ละชิ้นมีสถานะย่อย ว่าง / ถูกจอง / ถูกยืมอยู่ / ปิดใช้งาน
2. สถานะการจอง: รอรับของ / กำลังยืม / เกินกำหนด / คืนแล้ว / ยกเลิก
3. สถานะบัญชีผู้ใช้: ปกติ / ถูกพักสิทธิ์ชั่วคราว

ลำดับการพัฒนา:

ขั้นที่ 1 - ระบบบัญชีผู้ใช้: Login/Logout ด้วยอีเมล+รหัสผ่าน, ลืมรหัสผ่าน, แบ่งสิทธิ์นักศึกษา/เจ้าหน้าที่

ขั้นที่ 2 - ระบบคลังอุปกรณ์: แสดงรายการอุปกรณ์พร้อมจำนวนคงเหลือเรียลไทม์, ค้นหา/กรองหมวดหมู่, ฝั่งเจ้าหน้าที่เพิ่ม/แก้ไข/ปิดใช้งานอุปกรณ์ได้

ขั้นที่ 3 - ระบบการจอง: เลือกวันยืม-คืน (จำกัดจำนวนวันสูงสุด), ตรวจสอบไม่ให้จองซ้อนกันเมื่อของไม่พอ (ป้องกัน race condition), ลดจำนวนคงเหลือทันทีเมื่อจองสำเร็จ, สร้าง QR Code ผูกกับ Booking ID, ตั้งเวลาหมดอายุการจอง, นักศึกษายกเลิกจองเองได้ก่อนถึงขั้นตอนรับของ, ระบบยกเลิกอัตโนมัติเมื่อไม่มารับตามเวลา (คืนจำนวนคงเหลือทุกครั้งที่ยกเลิก)

ขั้นที่ 4 - ระบบแจ้งเตือนอีเมล: ส่งอีเมลยืนยันพร้อม QR Code ตอนจองสำเร็จ, ส่งอีเมลแจ้งยกเลิกอัตโนมัติกรณีไม่มารับ, ระบบตรวจสอบเป็นรอบ (scheduled job) วันละครั้งเพื่อส่งแจ้งเตือนใกล้ครบกำหนด (1 ครั้ง), ถึงกำหนด (1 ครั้ง), และเกินกำหนด (ซ้ำวันละครั้งจนกว่าจะคืน)

ขั้นที่ 5 - ระบบยืนยันรับอุปกรณ์ (ฝั่งเจ้าหน้าที่): สแกน/ค้นหา QR Code เพื่อดึงข้อมูลการจองขึ้นแสดง (ไม่ใช่การยืนยันอัตโนมัติ), ตรวจสอบสถานะการจองต้องเป็น "รอรับของ" เท่านั้น, บันทึกสภาพอุปกรณ์ก่อนส่งมอบ, ปุ่มยืนยันส่งมอบแยกต่างหากที่เจ้าหน้าที่ต้องกดเอง, เปลี่ยนสถานะเป็น "กำลังยืม" เมื่อกดยืนยันเท่านั้น

ขั้นที่ 6 - ระบบยืนยันรับคืน (ฝั่งเจ้าหน้าที่): ค้นหา/สแกน Booking ที่ต้องการรับคืน, บันทึกสภาพอุปกรณ์ตอนคืน (ถ้าชำรุดให้เปลี่ยนสถานะอุปกรณ์เป็นปิดใช้งานได้ทันที), ปุ่มยืนยันรับคืน, ระบบคำนวณอัตโนมัติว่าคืนตรงเวลาหรือไม่ ถ้าเกินกำหนดให้ตั้งสถานะบัญชีผู้ใช้เป็น "ถูกพักสิทธิ์" อัตโนมัติตามจำนวนวันที่ตั้งค่าไว้ (ค่าเริ่มต้น 1-2 วัน), จำนวนอุปกรณ์คงเหลือบวกกลับทันทีทุกกรณี

ขั้นที่ 7 - ระบบบทลงโทษ: เก็บค่าตั้งต้นของเกณฑ์วันที่เกินกำหนดและจำนวนวันพักสิทธิ์แบบปรับตั้งค่าได้, แสดงสถานะพักสิทธิ์พร้อมวันที่ปลดล็อกในหน้าโปรไฟล์ผู้ใช้, ปิดปุ่มจองอัตโนมัติระหว่างถูกพักสิทธิ์, ปลดสิทธิ์อัตโนมัติเมื่อครบกำหนดผ่าน scheduled job, เจ้าหน้าที่ปลดล็อกเองได้ในกรณีพิเศษ

ขั้นที่ 8 - ประวัติและแดชบอร์ด: หน้าประวัติการยืมของนักศึกษาแยกตามสถานะ, แดชบอร์ดสรุปภาพรวมฝั่งเจ้าหน้าที่ (จำนวนกำลังยืม/เกินกำหนด/ผู้ใช้ถูกพักสิทธิ์)

ข้อกำหนดสำคัญที่ต้องยึดตามทุกขั้นตอน:
- การสแกน QR Code ต้องเป็นแค่การดึงข้อมูล ห้ามเปลี่ยนสถานะอัตโนมัติ ต้องรอการกดยืนยันจากเจ้าหน้าที่เสมอ
- ทุกจุดที่มีการเปลี่ยนสถานะอุปกรณ์ (จอง/ยกเลิก/หมดเวลา/รับของ/คืนของ) ต้องอัปเดตจำนวนคงเหลือให้ถูกต้องแบบ atomic เพื่อป้องกันข้อมูลไม่ตรงกัน (race condition)
- สถานะพักสิทธิ์มีผลเฉพาะการจองใหม่เท่านั้น ไม่กระทบสิทธิ์การใช้งานอื่นของบัญชี
- ระบบแจ้งเตือนไม่จำเป็นต้องเรียลไทม์ ใช้ scheduled job ตรวจสอบวันละครั้งเพียงพอ แต่ข้อมูลจำนวนอุปกรณ์คงเหลือต้องเรียลไทม์เสมอ
```
